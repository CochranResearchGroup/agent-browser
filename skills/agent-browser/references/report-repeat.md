# Repeat and promote reviewed report knowledge

Use the existing SiteGuide teaching routines and composed playbook. Open the exact
candidate through the receiving application's teaching-review client and obtain
an actual operator decision. Work in a new task with newly requested dates;
never silently reuse demonstration dates or take visible account labels as
business-identity proof.

Check the intended report and date range against the actual CSV bytes. A download
event, prepared marker, file name or dispatched click is insufficient. On a lost
reply, read the original task operation and observe the result without repeating
its submission. Preserve peer tabs and unsaved drafts. A changed control should
produce a concrete assistance result or a verified adaptation using reviewed
knowledge, not an unsupported download workaround.

`review.recordFreshRepeat` imports a receiving-app verification reference bound to
exact guide/raw/content hashes, the operator decision, fresh task, report/dates,
CSV identity/digest and original submission ID. It executes no report itself.
`review.promote` permits reusable-version selection only after both trusted
review and repeat evidence reverify. Caller booleans and stored provenance labels
are never authority. The prior accepted bytes remain until the qualification
passes; failed or unavailable proof cannot replace them.

Unresolved questions block promotion. If optional clarification exists, the
receiving app must configure its authenticated answer reader so the grilling
verifier can recheck the current and original questions and attributed answers.
Missing or changed authority remains unverified. The ordinary candidate path
requires no clarification metadata or extra ceremony.

Use fresh operation IDs for new metadata intent and recover an interrupted save
with `lookupOperation` or the same exact operation. Reopen the returned immutable
revision before the next mutation. Stock MCP teaching inspection remains inert;
a fake validation or promotion record cannot grant execution permission. Real
Auth and private narrated acceptance keep their existing independent boundaries.
