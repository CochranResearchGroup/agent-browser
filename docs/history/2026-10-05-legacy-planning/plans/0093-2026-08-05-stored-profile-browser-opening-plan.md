## Goal

Open new, operator-visible browser processes against selected stored profiles
through the service-owned launcher contract. Prove exact profile binding,
process ownership, page target, stream addressability, and one-process-per-
profile safety from the installed runtime.

## Current Evidence

- The installed profile collection currently contains 440 retained profile
  records and 160 runtime-profile directories. Much of that inventory is old
  test or temporary history, so raw enumeration is not an operator launch
  decision.
- `last30days-facebook` and
  `auracall-chatgpt-wsl-chrome-2-consult` are the two available stored profiles
  with fresh authenticated target-readiness evidence and no service holder.
- Access-plan recommends `launch_new_browser` for both profiles with
  `exclusive_process`, `shared_browser_tabs`, and duplicate-process launch
  disabled.
- The documented CLI browser-capability preflight currently fails when
  `--browser-build` is supplied. Global flag cleaning removes that nested flag
  before the command parser consumes it, so the recommended no-launch gate is
  unusable even though access-plan has already selected a profile.
- The default profile is exclusively held by `litscout-e3-auracall`. It is not
  in this plan's launch scope.
- The RDP route-pool doctor reports both route displays, local embedding,
  public operator URLs, Guacamole permissions, and RDP backends ready. The
  workstation payload still has separate source-free provenance drift.

## Authority And Stop Conditions

- Launch only these two new daemon sessions:
  - `stored-last30days-social` with runtime profile `last30days-facebook` and
    target `https://www.facebook.com/`;
  - `stored-auracall-chatgpt` with the registered AuraCall profile path and
    target `https://chatgpt.com/`.
- Use access-plan-selected browser builds, remote-headed posture, RDP gateway
  view, manual attached-desktop input, and shared display isolation.
- Launch the social profile first. Stop before the second launch on the first
  profile, process, target, stream, lifecycle, or route mismatch.
- Do not close, relaunch, or modify the retained `default`,
  `litscout-e3-auracall`, or `wsl-chrome-3` browser lanes.
- Do not create a second process for either selected profile when a live holder
  appears. Reuse or stop according to the fresh access-plan readback.
- Loading the requested landing pages is authorized. Page interaction,
  posting, messaging, account mutation, login mutation, and external
  transmission are outside this plan.
- Leave successful new browsers running for the operator. Clean up only a
  failed partial canary created by this plan.

## Implementation And Execution

### Slice A: Repair The No-Launch Gate

- Add a public CLI parsing regression that exercises `parse_flags`,
  `clean_args`, and `parse_command` together.
- Preserve CLI `--browser-build`, `--runtime-profile`, `--profile`, and
  `--headed` values when the nested command is
  `service browser-capability preflight`.
- Prove the access-plan-generated preflight commands succeed without launching
  Chrome.

### Slice B: Installed Runtime And Launcher Proof

- Run Rust format, strict Clippy, focused parser tests, dashboard launcher
  eligibility tests, and selected validation.
- Publish the corrected executable while preserving current daemon and browser
  processes.
- Verify the dashboard manifest and direct profile search/launcher workflow.

### Slice C: Stored-Profile Launches

- Re-read profile allocation and access-plan immediately before each launch.
- Start each named session through the same CLI arguments generated by the
  dashboard launcher.
- For each browser, prove:
  - exact daemon session and browser PID;
  - exact runtime profile or normalized user-data directory;
  - CDP reachability and page target identity;
  - service-owned browser/session/profile relationships;
  - usable dashboard CDP or RDP stream metadata;
  - no second process group on the same profile.
- Verify the previously retained browser lanes retain their original PIDs and
  endpoints.
