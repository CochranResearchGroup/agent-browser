# Observability Dashboard

Monitor agent-browser sessions in real time with a local web dashboard showing a live browser viewport and command activity feed.

## Usage

The dashboard is bundled into the binary and requires no separate install. Start the server and open any session:

```bash
agent-browser dashboard start
agent-browser open example.com
```

Then open `http://localhost:4848` in your browser to see the live dashboard.

All sessions automatically stream to the dashboard. No extra flags are needed.

## Development dashboard

Experimental workstation builds have a separate runtime at
<code>http://127.0.0.1:4948</code>. Run <code>pnpm build:dashboard</code>, then
<code>pnpm build:development-candidate</code>, then run
<code>pnpm development-runtime:install</code>. The installer stages an immutable
development generation and activates only the
<code>agent-browser-dev-&#42;.service</code> user units. It does not replace or
restart the production executable, runtime host, or dashboard.
The isolated runtime host starts from the durable
<code>development-default</code> lane manifest on fixed stream port 4951.
The stable <code>agent-browser-dev</code> launcher selects the same dev
pseudo-home, socket, auth store, and environment identity for direct CLI use.
It also pins one Linux-compatible browser executable so a Linux-only managed
profile cannot accidentally inherit a Windows browser manifest. Set
<code>AGENT_BROWSER_DEV_BROWSER_EXECUTABLE</code> before publication only for a
reviewed absolute executable.
Production <code>agent-browser install doctor</code> scopes its daemon census to
the exact production socket path. The sibling <code>agent-browser-dev</code>
namespace is excluded from production runtime-host and executable-generation
multiplicity.

The development candidate uses the optimized Cargo <code>ci</code> profile at
<code>cli/target/ci/agent-browser</code>. Reserve
<code>pnpm build:native</code> for the final production or release gate. The
resource-aware Cargo wrapper defaults to eight jobs and automatically uses
<code>sccache</code> and <code>mold</code> when installed. Set
<code>AGENT_BROWSER_CARGO_CACHE=off</code> or
<code>AGENT_BROWSER_CARGO_FAST_LINKER=off</code> to disable either accelerator
for one command. <code>pnpm benchmark:cargo-build-jobs</code> reruns the isolated
4/6/8-job comparison without cleaning the shared target directory.

Use <code>pnpm development-runtime:status</code> for a readback and
<code>pnpm development-runtime:doctor</code> for the acceptance checks. The
doctor requires the shared root-owned
<code>agent-browser-lease-authority.socket</code> to be loaded, enabled, active,
owned by root, assigned to the <code>agent-browser</code> group, and mode
<code>0660</code>. Development services never create a second authority daemon.
Use the reviewed one-sudo <code>pnpm install:privileges -- --apply</code>
bootstrap when this check fails. The
development dashboard displays a persistent Development badge, and
<code>/api/runtime/manifest</code> reports
<code>runtimeEnvironment: "development"</code>. The separate Cooper inventory
entry named <code>agent-browser-dev</code> owns external ingress. It initially
publishes the dashboard and an isolated presentation provider on local port
8093. The provider owns six development-only route identities and must not use
the production Guacamole provider.
Publish experimental agent guidance with
<code>pnpm development-runtime:skill-sync</code> and verify it with
<code>pnpm development-runtime:skill-status</code>. The target is inside the
development pseudo-home, not the shared user-scoped production skill.

The development doctor also reports presentation-provider state. A missing
provider is explicitly <code>unconfigured</code> and nonblocking for dashboard
and CDP work. Provider-backed acceptance sets
<code>AGENT_BROWSER_DEV_PRESENTATION_PROVIDER_REQUIRED=1</code>; once a provider
manifest exists, namespace or manifest drift is blocking. Development
Guacamole, XRDP, display, route, database, secret, cleanup, and ingress effects
remain a separately reviewed operation.
Before staging, set <code>AGENT_BROWSER_DEV_PUBLIC_OPERATOR_URL</code> to the
reviewed public HTTPS origin and
<code>AGENT_BROWSER_DEV_EXTERNAL_INGRESS_REVISION</code> to the immutable
reviewed Cooper deployment revision or receipt ID. Both are required together,
and the provider retains their deterministic binding digest. Loopback remains
a local diagnostic URL and is never an operator handoff.
Review and stage those effects with
<code>pnpm development-runtime:provider-plan</code> and
<code>pnpm development-runtime:provider-stage</code>, then run
<code>pnpm development-runtime:provider-preflight</code>. The only apply form is
<code>pnpm development-runtime:provider-apply -- --apply --defer-ingress</code>.
Publish Cooper ingress only after the provider-ready checkpoint. A green
provider doctor is not capacity proof; development Service Status must also
report a non-null <code>presentationCapacity</code> before capacity acceptance.
Elastic changes require an explicit one-route command:
<code>pnpm development-runtime:provider-scale-out -- --apply</code> or
<code>pnpm development-runtime:provider-scale-in -- --apply</code>. Scale-out
uses current memory, swap, load, and file-handle admission. Scale-in waits for
Scale-out also requires the installed helper to prove exact, idempotent
route-session reclamation before it provisions anything. Scale-in waits for
cooldown and refuses a route with browser, session, viewer, controller,
acquisition, handoff, restoration, or cleanup references. Ambiguous or partial
effects are quarantined with an exact development cleanup obligation and never
authorize production cleanup.
Use <code>pnpm smoke:development-dashboard-auth -- --dashboard-url
https://agent-browser-dev.ecochran.dyndns.org</code> to verify login, the
session cookie, authenticated service API access, and the development manifest
without printing dashboard credentials.
Run <code>pnpm smoke:development-browser-launch</code> to verify three
disposable open, URL-read, close, and process-residue cycles through the stable
development command. The smoke also proves that production identities remain
unchanged.

Old development generations are collected with
<code>pnpm development-runtime:gc</code>. The collector always retains the
selected generation, running generation executables, and the configured number
of newest rollback candidates.
Service resource GC is separately fail-closed: an OS process must have positive
development-environment ownership before it can become a development cleanup
candidate. Absence from the isolated development ledger is not ownership.

`dashboard start` keeps port 4848 as stable ingress and starts the current
generation backend on the next port. The ingress retains the prior selected
backend as a draining fallback. It changes selection only after a shadow
candidate passes its runtime-manifest probe and authenticated operator-journey
proof.

```bash
agent-browser dashboard ingress status
agent-browser dashboard ingress stage --expected-revision 1 --generation candidate-1 --port 4850 --manifest-sha256 <sha256>
agent-browser dashboard ingress commit --expected-revision 2 --evidence <presentation-evidence.json>
agent-browser dashboard ingress rollback --expected-revision 2 --generation candidate-1
```

The mutating ingress commands use revision compare-and-swap. `commit` probes
the candidate again and refuses selection when its manifest changed or the
evidence does not describe a ready authenticated operator surface. An
authenticated durable-handoff response served by the staged candidate
automatically performs this same checked commit when the response is ready.
The explicit `commit --handoff-id` form remains the recovery path for a receipt
that was persisted before automatic selection completed. Set
`AGENT_BROWSER_DASHBOARD_INGRESS_STATE` only for an isolated private registry.
Set `AGENT_BROWSER_DASHBOARD_AUTH_DIR` as well when a fixture must isolate the
auth store, bootstrap credentials, and managed environment file.

## Open a durable RDP handoff

When an agent gives you an RDP or Guacamole browser, open the authenticated
`/remote-view/<handoff-id>` link. Bookmark and reopen that link if the provider
route changes. Do not bookmark the raw Guacamole URL shown in diagnostic
evidence.

See [Open and reconnect an RDP browser](/remote-view) for the exact agent and
operator workflow, takeover behavior, and troubleshooting steps.

## Dashboard login

The dashboard protects its operator APIs with an app-owned login screen. On
first start it creates `~/.agent-browser/dashboard-auth.json` with hashed
superuser credentials and writes bootstrap credentials to the mode-0600 file
`~/.agent-browser/dashboard-auth.env`.

The default `admin` account is a superuser. A `codex` superuser is also created
for agent observation through trusted ingress. The dashboard records
`AGENT_BROWSER_DASHBOARD_AUTH_FILE` in `~/.agent-browser/.env` so foreground
runs and the user-scoped service use the same auth store.

### Custom stream port

By default each session binds its WebSocket stream server to an OS-assigned port. To use a specific port, set the `AGENT_BROWSER_STREAM_PORT` environment variable:

```bash
AGENT_BROWSER_STREAM_PORT=9223 agent-browser open example.com
```

You can also use the runtime commands to control streaming on a running session:

```bash
agent-browser stream enable --port 9223
agent-browser stream status
agent-browser stream disable
```

## Dashboard features

The dashboard is an operations console with routeable operator areas:

Dashboard sections are URL-addressable. Use <code>/service</code> for the
Service view, <code>/browsers</code> for Browser sessions, and
<code>/activity</code> for the activity stream. The Service view preserves its
active record workspace in <code>?view=service:&lt;name&gt;</code> with values
such as <code>service:browsers</code>, <code>service:profiles</code>,
<code>service:incidents</code>, <code>service:sessions</code>,
<code>service:tabs</code>, <code>service:jobs</code>, and
<code>service:events</code>. The left workspace navigator separately persists
the selected workspace, browser, session, tab, profile, and job query
parameters so refreshes and handoff links reopen the same operational view.

## Local Runtime Publish

Dashboard source changes are not visible on the long-running local dashboard
service until the dashboard export is embedded into the installed CLI and the
user service is restarted. For operator-visible QA on
<code>http://127.0.0.1:4848</code>, run:

```bash
pnpm publish:local-dashboard -- --expect-marker "Stream port"
```

The command builds <code>packages/dashboard/out</code>, rebuilds the local CLI,
and submits that candidate to the canonical workstation transaction. The
installer owns census, admission drain, runtime transfer, selector commit,
rollback, and stable-ingress reconciliation. The publisher never directly
replaces <code>~/.local/bin/agent-browser</code> and then smokes the live URL.
The smoke reads <code>/api/runtime/manifest</code> from the running service and
records the served package version, service UI contract, embedded dashboard
SHA-256, supported UI features, current executable path, and current executable
SHA-256. The publish command fails when that live manifest does not match the
installed binary it just wrote. Use <code>pnpm smoke:local-dashboard-runtime
-- --expect-marker "Stream port"</code> to verify the already installed service
without replacing the binary. If the dashboard detects a stale or missing
manifest, it renders a <code>Runtime contract drift</code> warning above the
control surface. After login, the dashboard polls the authenticated
<code>/api/runtime/health</code> endpoint every ten seconds. Its
<code>agent-browser.runtime-health.v1</code> response compares active daemon
executable, package, and stream metadata with the running binary, then renders
<code>Runtime status out of sync</code> as soon as drift appears. Detection is
read-only and never restarts an active session automatically. The same health
response includes every installed named daemon supervisor, its restart state,
fixed stream port, published port, stream reachability, and executable match.
Port conflicts, executable drift, stopped units, and exhausted restart limits
therefore degrade the dashboard immediately instead of waiting for browser UX
to fail. The persistent runtime summary also shows dashboard-process,
runtime-host, legacy-daemon, and executable-generation counts from the shared
multiplicity authority. It reports runtime-monitor freshness, tracked and
missing cleanup obligations, protected versus reclaimable RSS, unowned RSS,
the most recent generation-retention result, and any blocking repeated-failure
incident. These are read-only summaries of the same receipts used by
workstation reconciliation and install doctor.
<code>agent-browser install doctor --json</code> and
<code>agent-browser doctor remote-view --json</code> include the same
<code>dashboardRuntime</code> manifest, so CLI and dashboard readbacks describe
the same installed binary and embedded UI bundle.

The health contract keeps four independent axes: runtime, workstation
convergence, profile access, and request-scoped acquisition. Only blocking
runtime or convergence findings produce the dashboard convergence warning.
Legacy profile identity ambiguity appears as an access advisory. The profile
editor exposes shared-local, restricted, and exclusive modes plus
administrator, participant, and observer presets. A profile-config save
preserves the current access policy; policy changes use their own
revision-fenced service request.

An available profile tile provides <strong>Open browser</strong>, which opens
the guided launcher with that exact profile selected and runs its no-launch
access-plan preflight. Every live service-owned browser provides
<strong>Close</strong> in the workspace tree and Service browser table.
Detected non-owned browsers retain screenshot, watch, and borrowed-input
controls without lifecycle ownership.

## WebSocket protocol

The dashboard connects to the same WebSocket endpoint used by [Streaming](/streaming), with additional message types for observability:

### Command events

Sent when a command begins executing:

```json
{
  "type": "command",
  "action": "click",
  "id": "r123",
  "params": { "selector": "@e5" },
  "timestamp": 1711367000000
}
```

### Result events

Sent when a command finishes:

```json
{
  "type": "result",
  "id": "r123",
  "action": "click",
  "success": true,
  "data": {},
  "duration_ms": 45,
  "timestamp": 1711367000045
}
```

### Console events

Sent when the browser logs to the console:

```json
{
  "type": "console",
  "level": "log",
  "text": "Page loaded",
  "args": [{"type": "string", "value": "Page loaded"}],
  "timestamp": 1711367000100
}
```

The `args` array contains the raw CDP `Runtime.consoleAPICalled` arguments for programmatic access. Object arguments include preview data (e.g. `{userId: "abc", count: 42}` instead of `"Object"`).

These are in addition to the existing `frame`, `status`, and `error` message types documented on the [Streaming](/streaming) page.

## Architecture

The dashboard is a Next.js static export (`output: 'export'`) that produces plain HTML, CSS, and JS. It lives at `packages/dashboard/` in the monorepo and is built with:

```bash
pnpm build:dashboard
```

The dashboard is embedded into the CLI binary at compile time using `rust-embed`. Plain HTTP requests serve the embedded dashboard assets, while WebSocket upgrade requests are handled as before.

## AI Chat

The dashboard includes an optional AI chat panel powered by the [Vercel AI Gateway](https://vercel.com/docs/ai-gateway). When enabled, a **Chat** tab appears in the right pane alongside Activity, Console, Network, Storage, and Extensions.

### Setup

The Chat tab is always visible. Set the API key to enable responses:

```bash
export AI_GATEWAY_API_KEY=gw_your_key_here
agent-browser dashboard start
```

Optionally override the gateway URL or model:

```bash
export AI_GATEWAY_URL=https://ai-gateway.vercel.sh   # this is the default
export AI_GATEWAY_MODEL=openai/gpt-4o-mini           # default: anthropic/claude-sonnet-4.6
```

### How it works

The Rust server proxies chat requests from the dashboard to the Vercel AI Gateway and streams responses back using the Vercel AI SDK's UI Message Stream protocol. The dashboard frontend uses `useChat` from `@ai-sdk/react` with `DefaultChatTransport`.
