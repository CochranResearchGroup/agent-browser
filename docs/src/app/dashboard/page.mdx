# Observability Dashboard

Select, inspect, share and continue browser tasks in one native workspace. Its compact browser/tab rail keeps the owned Remote View desktop central; Handoffs and diagnostics open when needed.

## Open a manual browser

Use **Open browser** in the thin top toolbar. The default is a disposable,
CDP-free browser on a blank page. Choose Chrome or Chromium, inspect exact
installed build/version details, and choose an existing profile or create a
named durable profile. An optional starting URL is restricted to HTTP, HTTPS
or <code>about:blank</code>. Manual tasks stay open until explicitly closed,
including after closing the dashboard.

Compatible connected profiles use an independent task/tab. A CDP-free browser
has one owned window: return to the existing task or choose another profile.
Use Profile Lab for an independent copy. A build change on an original closed
profile requires explicit migration/sign-in risk confirmation.

A lost reply retains the original operation. **Inspect original launch** reads
its result without replaying creation. Only a confirmed refusal with no effects
permits revised choices. A successful allocation selects the exact task; the
existing native consumer independently qualifies desktop visibility and keeps
Remote View's native input, recording and narration controls.

## Profiles and intended identities

The toolbar wrench opens **Profiles and SiteGuides**. Profiles can have several
intended site/account/organization associations. Search names, account labels
and site context. Intended use, observed identity and authentication freshness
are separate evidence. Saving intended associations never verifies login.
Explicit profiles remain selected. Automatic choice requires a unique,
compatible exact intended identity; ambiguity and conflicts require a choice.
Public profile policy controls read, use and association updates.

Dashboard failures are postmortem evidence. The dashboard observes failed
mutating HTTP actions without changing their behavior, reports unusable
Guacamole frames and durable handoffs, and runs a watchdog for CDP feeds that
connect or declare screencasting without delivering a usable frame. These
authenticated observations are appended to the service failure journal and
can be reviewed through <code>GET /api/service/failures?limit=100</code>. The
reporter never sends the current page URL, iframe URL, raw handoff ID,
credentials, headers, bearer material, or page content.

The operator workspace reuses trusted ingress sign-in and retains supported
local API sessions. Native Remote View retains its existing viewer authentication.
Native workspace embedding requires the dashboard and Remote View to share a
public origin. An iframe handoff selects Remote View's existing workspace mode;
Remote View enforces its same-origin framing policy. Opening the durable link
normally retains the standalone native viewer. This adds no viewer grant.
Service Status includes <code>browserRuntime.workspace</code>, a read-only
projection of the current managed browsers, sessions, tabs, supplied task
metadata and independent retention records. Its <code>reported</code> state
identifies owner-published inventory; it does not establish process liveness
or native viewer readiness. Debugger endpoints and private launch environment
are omitted.

Diagnostics → Selection offers Focus for an exact current owned tab. Missing, foreign, absent or stale targets cannot request focus. Refresh the workspace to obtain current evidence. Native focus requests share the existing per-desktop queue; an older selection cannot replace current feedback or start stale queued work. Accepted-request feedback is not independent proof of physical window focus.

After a successful Chat inspection, choose **Record as accepted** or **Record as rejected** to add your judgment to Activity. The entry retains the original workspace, browser, task, tab, profile, run, packet hash, evidence references and reviewer; observation prose and ledger paths stay out of Activity. Recording executes no suggested action and does not establish readiness or authority. Return to the original selection to review its result. An opposite verdict appends a correction; repeating the current verdict adds nothing. Activity keeps its existing 500-event bound, session-scoped Clear and opt-in Persist setting. With Persist off, reviews last only for the current page; unavailable browser storage is reported rather than described as saved.

Selected-workspace diagnostics and contextual chat follow the explicitly selected owned tab. If its target disappears, they do not substitute another page in the same browser. Browser-wide activity remains scoped to its owner. Diagnostic copies and contextual chat exports omit URL userinfo, query strings and fragments; opaque URL payloads are omitted. Live URLs and explicit Copy URL remain unchanged. This does not remove arbitrary secrets from prose or path segments.

Tab descriptions use live observed page titles when available, then supplied task labels. Opaque data URLs use readable document labels; Properties and Copy URL retain the original URL. Inventory reads do not select tabs.

In the default browser workspace, open a tab’s SVG overflow menu or use its
context menu (<kbd>Shift+F10</kbd>) for Properties and Copy URL. Properties shows supplied
origin and purpose alongside current browser, profile, desktop, URL, title and
status. Missing values remain Unknown; descriptive names are not identity proof.
Copy URL copies the task URL without creating a handoff or changing selection.
Close Tab confirms one managed task before requesting its exact target through the
existing browser owner. It requires authenticated dashboard access and current
profile permission to close any tab. Cancelling sends no request. A confirmed
close preserves peer tabs; closing the final owned tab also closes its browser.
If close cannot be confirmed, refresh inventory and inspect permission before
trying again.

Share prepares the exact existing task through the public handoff helper and
shows its opaque native link in Handoffs. It preserves the selected peer and
does not navigate the task. Use the small Handoffs rail control to reopen the
panel, then copy or open the same link through existing Remote View authentication.

Handoffs lists retained owner records even after target expiry, with supplied
origin, creation/use status and separate link/tab policies. Inspect shows task
context; Copy and Open reuse the opaque link. A failed refresh retains the last
reported records. Unavailable inventory is distinct from an empty list.
The drawer expands on wide screens. Sort by task name, creation time or link
expiry using the column controls. Inactive links are amber and hidden until
Show inactive is enabled; an expired task can still have an active link.
Icon controls expose hover help. A task without a native desktop uses its
available browser stream; otherwise it reports desktop availability separately
from a missing tab.
The rail joins Remote View application windows with live browser process and
exact tab observations. It also lists current native browser windows from other
applications, including hidden groups, without inventing managed task ownership.
These windows use Remote View’s existing connection and window controls; managed
task actions remain available only for owned tasks. Legacy daemon history is
confined to diagnostics rather than treated as native browser presence. Empty desktops, ended tabs and unverified managed records
are excluded. Failed or stale observations preserve selection and retained links;
a later successful refresh can restore the same tab without recreating it.
The native rail reads the dedicated workspace projection and polls three seconds
after each completed read. On startup only, wholly unknown tab presence gets up
to three catch-up reads after delays of 250, 500 and 1000 milliseconds, ending on live, absent or failed
evidence. Catch-up revalidates the shared response cache. Both HTTP listeners read the current owner snapshot
directly, without the diagnostic transport, CLI fallback or one-second status cache.
Service reconciliation and workstation diagnostics run only on diagnostic surfaces. Observation freshness expires
independently after 30 seconds using elapsed time, even if the next read stalls.
Search matches displayed tab labels and URLs, excluding embedded document payloads.



Policies opens link lifetime controls for a retained record. Choose Perpetual or
a finite duration in seconds; the finite window starts when saved. This leaves
tab lifetime and unused retention unchanged. Expired links remain revoked.

Tab inactivity and unused retention have separate saves in Policies. Tab expiry
uses the task's last activity; unused retention starts a new wait-for-human window
when saved. Choose finite seconds or keep the unused task until used. A current
wait appears as Awaiting use; Inspect preserves the original first-use timestamp.

Delete link asks for confirmation and revokes only the selected link. Its browser
and tabs stay open; Cancel has no effect. Unconfirmed deletion keeps the record
visible and offers refresh guidance without an automatic retry.

## Usage

The dashboard is bundled into the binary and requires no separate install. Start the server and open any session:

```bash
agent-browser dashboard start
agent-browser open example.com
```

Then open `http://localhost:4848` in your browser to see the live dashboard.

Current browsers and tabs appear automatically. Select a task to view its owned desktop.

`dashboard start` keeps port 4848 as stable ingress and starts the current
generation backend on the next port. The ingress retains the prior selected
backend as a draining fallback. It changes selection only after a shadow
candidate passes its runtime-manifest probe and authenticated operator-journey
proof.

```bash
agent-browser dashboard ingress status
agent-browser dashboard ingress stage --expected-revision 1 --generation candidate-1 --port 4850 --manifest-sha256 <sha256>
agent-browser dashboard ingress commit --expected-revision 2 --evidence <presentation-evidence.json>
agent-browser dashboard ingress rollback --expected-revision 2 --generation candidate-1
```

The mutating ingress commands use revision compare-and-swap. `commit` probes
the candidate again and refuses selection when its manifest changed or the
evidence does not describe a ready authenticated operator surface. An
authenticated durable-handoff response served by the staged candidate
automatically performs this same checked commit when the response is ready.
The explicit `commit --handoff-id` form remains the recovery path for a receipt
that was persisted before automatic selection completed. Set
`AGENT_BROWSER_DASHBOARD_INGRESS_STATE` only for an isolated private registry.
Set `AGENT_BROWSER_DASHBOARD_AUTH_DIR` as well when a fixture must isolate the
auth store, bootstrap credentials, and managed environment file.

When an agent gives you an RDP or Guacamole browser, open the authenticated

For example, the synthetic mapping <code>{'{"operator":"admin","reader":"codex"}'}</code>
preserves the default admin superuser and codex observer roles. It grants no role
without explicit configuration. The backend sends the cookie directly to the
owner with metadata derived from the reviewed URL. Only owner HTTP200 with one
<code>Remote-User</code> and a known mapping establishes identity; caller
identity headers never authenticate. Redirects are not followed. Owner302/303/401
requires sign-in; denied or unmapped users receive403; malformed or unavailable
verification receives503. Partial or invalid configuration fails closed. Recovery
preserves the selected browser URL and distinguishes sign-in, access denial,
redirected content and service failure.

With all three settings absent, supported local and machine authentication
continues through <code>POST /api/dashboard-auth/login</code> and signed sessions.
First start creates private <code>~/.agent-browser/dashboard-auth.json</code> and
mode-0600 <code>~/.agent-browser/dashboard-auth.env</code>. The admin user is a
superuser; codex is an observer. The existing auth-file and auth-directory
overrides remain supported. Valid local sessions take precedence and renew their
thirty-day cookie on status read. Ingress identities never mint local cookies.
The returned user has <code>authenticationSource</code> set to ingress or local.
**End local session** ends a local cookie; ingress sign-out remains provider-owned.
Website account authentication and Native viewer access remain separate.
Installing or configuring this bridge and qualifying an actual ingress/Native
workflow require their own evidence; source fixtures do not establish those results.

### Custom stream port

By default each session binds its WebSocket stream server to an OS-assigned port. To use a specific port, set the `AGENT_BROWSER_STREAM_PORT` environment variable:

```bash
AGENT_BROWSER_STREAM_PORT=9223 agent-browser open example.com
```

You can also use the runtime commands to control streaming on a running session:

```bash
agent-browser stream enable --port 9223
agent-browser stream status
agent-browser stream disable
```

## Dashboard features

Open <code>/</code> or <code>/browsers</code> for the default native browser
workspace. Collapse or resize its rail, select a tab and use Properties, Copy
URL, Share or scoped Close Tab. Handoffs opens retained records and their
independent policies on demand.

The toolbar Subsystem health SVG opens a side drawer with separate inventory, browser runtime, Native desktop readiness and selected viewer evidence. Gray means unverified or stale, amber means attention, red means unavailable and green means the reported checks pass. Detailed read-only checks run only when opening or refreshing the drawer, expire after 30 seconds and time out after eight seconds. They add no recurring diagnostic polling or automatic repair. A reachable service or prepared handoff does not prove a connected Native display.

Use Diagnostics at <code>/service</code> for Service inspection, Selection,
Activity, Chat, Console, Network, Storage, Extensions and runtime health.
<code>/activity</code> opens the Activity tool. Diagnostic viewing controls
return to the same browser workspace. Service record selection preserves
<code>?view=service:&lt;name&gt;</code>, including
<code>service:browsers</code>, <code>service:profiles</code>,
<code>service:incidents</code>, <code>service:sessions</code>,
<code>service:tabs</code>, <code>service:jobs</code> and
<code>service:events</code>. Workspace, browser, session, tab, profile and job
query fields preserve the requested context across refresh.

## Local Runtime Publish

Dashboard source changes are not visible on the long-running local dashboard
service until the dashboard export is embedded into the installed CLI and the
user service is restarted. For operator-visible QA on
<code>http://127.0.0.1:4848</code>, run:

```bash
pnpm publish:local-dashboard -- --expect-marker "Stream port"
```

The command builds <code>packages/dashboard/out</code>, rebuilds the local CLI,
and submits that candidate to the canonical workstation transaction. The
installer owns census, admission drain, runtime transfer, selector commit,
rollback, and stable-ingress reconciliation. The publisher never directly
replaces <code>~/.local/bin/agent-browser</code> and then smokes the live URL.
The smoke reads <code>/api/runtime/manifest</code> from the running service and
records the served package version, service UI contract, embedded dashboard
SHA-256, supported UI features, current executable path, and current executable
SHA-256. The publish command fails when that live manifest does not match the
installed binary it just wrote. Use <code>pnpm smoke:local-dashboard-runtime
-- --expect-marker "Stream port"</code> to verify the already installed service
without replacing the binary. If the dashboard detects a stale or missing
manifest, it renders a <code>Runtime contract drift</code> warning above the
control surface. After login, the dashboard polls the authenticated
<code>/api/runtime/health</code> endpoint every ten seconds. Its
<code>agent-browser.runtime-health.v1</code> response compares active daemon
executable, package, and stream metadata with the running binary, then renders
<code>Runtime status out of sync</code> as soon as drift appears. Detection is
read-only and never restarts an active session automatically. The same health
response includes every installed named daemon supervisor, its restart state,
fixed stream port, published port, stream reachability, and executable match.
Port conflicts, executable drift, stopped units, and exhausted restart limits
therefore degrade the dashboard immediately instead of waiting for browser UX
to fail. The persistent runtime summary also shows dashboard-process,
runtime-host, legacy-daemon, and executable-generation counts from the shared
multiplicity authority. It reports runtime-monitor freshness, tracked and
missing cleanup obligations, protected versus reclaimable RSS, unowned RSS,
the most recent generation-retention result, and any blocking repeated-failure
incident. These are read-only summaries of the same receipts used by
workstation reconciliation and install doctor.
<code>agent-browser install doctor --json</code> and
<code>agent-browser doctor remote-view --json</code> include the same
<code>dashboardRuntime</code> manifest, so CLI and dashboard readbacks describe
the same installed binary and embedded UI bundle.

The health contract keeps four independent axes: runtime, workstation
convergence, profile access, and request-scoped acquisition. Only blocking
runtime or convergence findings produce the dashboard convergence warning.
Legacy profile identity ambiguity appears as an access advisory. The profile
editor exposes shared-local, restricted, and exclusive modes plus
administrator, participant, and observer presets. A profile-config save
preserves the current access policy; policy changes use their own
revision-fenced service request.

An available profile tile provides <strong>Open browser</strong>, which opens
the guided launcher with that exact profile selected and runs its no-launch
access-plan preflight. Every live service-owned browser provides
<strong>Close</strong> in the workspace tree and Service browser table.
Detected non-owned browsers retain screenshot, watch, and borrowed-input
controls without lifecycle ownership.

## WebSocket protocol

The dashboard connects to the same WebSocket endpoint used by [Streaming](/streaming), with additional message types for observability:

### Command events

Sent when a command begins executing:

```json
{
  "type": "command",
  "action": "click",
  "id": "r123",
  "params": { "selector": "@e5" },
  "timestamp": 1711367000000
}
```

### Result events

Sent when a command finishes:

```json
{
  "type": "result",
  "id": "r123",
  "action": "click",
  "success": true,
  "data": {},
  "duration_ms": 45,
  "timestamp": 1711367000045
}
```

### Console events

Sent when the browser logs to the console:

```json
{
  "type": "console",
  "level": "log",
  "text": "Page loaded",
  "args": [{"type": "string", "value": "Page loaded"}],
  "timestamp": 1711367000100
}
```

The `args` array contains the raw CDP `Runtime.consoleAPICalled` arguments for programmatic access. Object arguments include preview data (e.g. `{userId: "abc", count: 42}` instead of `"Object"`).

These are in addition to the existing `frame`, `status`, and `error` message types documented on the [Streaming](/streaming) page.

## Architecture

The dashboard is a Next.js static export (`output: 'export'`) that produces plain HTML, CSS, and JS. It lives at `packages/dashboard/` in the monorepo and is built with:

```bash
pnpm build:dashboard
```

The dashboard is embedded into the CLI binary at compile time using `rust-embed`. Plain HTTP requests serve the embedded dashboard assets, while WebSocket upgrade requests are handled as before.

## AI Chat

The dashboard includes an optional AI chat panel powered by the [Vercel AI Gateway](https://vercel.com/docs/ai-gateway). When enabled, a **Chat** tab appears in the right pane alongside Activity, Console, Network, Storage, and Extensions.

### Setup

The Chat tab is always visible. Set the API key to enable responses:

```bash
export AI_GATEWAY_API_KEY=gw_your_key_here
agent-browser dashboard start
```

Optionally override the gateway URL or model:

```bash
export AI_GATEWAY_URL=https://ai-gateway.vercel.sh   # this is the default
export AI_GATEWAY_MODEL=openai/gpt-4o-mini           # default: anthropic/claude-sonnet-4.6
```

### How it works

The Rust server proxies chat requests from the dashboard to the Vercel AI Gateway and streams responses back using the Vercel AI SDK's UI Message Stream protocol. The dashboard frontend uses `useChat` from `@ai-sdk/react` with `DefaultChatTransport`.
