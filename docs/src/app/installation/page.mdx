# Installation

## GitHub release binary (recommended)

Download the native Rust binary from this fork's GitHub releases. Pick the asset
for your platform from the latest release, then put it on your PATH.

```bash
VERSION=v0.28.0
curl -L -o ~/.local/bin/agent-browser \
  https://github.com/CochranResearchGroup/agent-browser/releases/download/$VERSION/agent-browser-linux-x64
chmod +x ~/.local/bin/agent-browser
agent-browser install  # Download Chrome from Chrome for Testing (first time)
agent-browser install stealthcdp-chromium  # Optional preferred patched Chromium
agent-browser install doctor  # Check binary drift and launch readiness
agent-browser install --with-deps --with-remote-view-privileges  # Linux RDP/Guacamole desktop setup
agent-browser install workstation --dry-run --json  # Preview source-free workstation payload
agent-browser install workstation --apply --json  # Install and reconcile a fresh Ubuntu workstation
agent-browser install workstation status --json  # Read the latest redacted upgrade transaction
agent-browser install workstation finalize --json  # Retire rollback only after accepted readiness review
agent-browser install workstation gc --dry-run --json  # Preview safe old-generation cleanup
```

This is the fastest option. Commands run through the native Rust CLI directly
with sub-millisecond parsing overhead.

For source-checkout capacity work, `AGENT_BROWSER_RDP_ROUTE_USER_POOL_JSON` may declare an arbitrary bounded list of route users and Guacamole connection names. This source configuration does not change the installed production runtime until a separately authorized workstation reconciliation applies it.

## Package-manager channels

npm, Homebrew, and Cargo are not authoritative release channels for this fork.
Use GitHub release binaries or build from source.

## From source

```bash
git clone https://github.com/CochranResearchGroup/agent-browser
cd agent-browser
pnpm install
pnpm build
pnpm build:native
./bin/agent-browser install
```

## Linux dependencies

On Linux, install system dependencies:

```bash
agent-browser install --with-deps
```

For Guacamole and RDP remote viewing on Linux, include the one-time privileged
setup in the installer:

```bash
agent-browser install --with-deps --with-remote-view-privileges
```

This installs the <code>agent-browser</code> group, the root-owned helper at
<code>/usr/local/libexec/agent-browser/agent-browser-privileged-helper</code>,
and the sudoers rule that lets members of that group configure RDP route users,
restart XRDP, and grant route-display access without repeated sudo prompts.
New route-pool users get an idle Openbox session that keeps XRDP alive without
starting a foreground terminal, so <code>remote-view open</code> can make the
browser the operator-visible window.
Routine workstation reconciliation preserves live XRDP desktops. Route-user
and credential changes take effect at the next login without restarting
<code>xrdp-sesman</code>, whose replacement cannot adopt an existing Xorg
session.
After applying, open a new shell or run <code>newgrp agent-browser</code>, then
verify with <code>agent-browser doctor remote-view</code>.
When <code>--with-deps</code> is combined with
<code>--with-remote-view-privileges</code>, the remote-view privilege installer
runs first so its explicit <code>sudo -v</code> boundary authorizes the later
dependency installation.
Re-running the command on an already-provisioned machine exits before any
privileged changes when the helper, sudoers policy, group, and membership are
already ready. Readiness is based on the bounded helper command and capability
contract, so a compatible root-owned helper is retained even when its bytes
differ from the newly bundled helper. Recurring route-user, XRDP restart, and
display-access maintenance uses passwordless <code>sudo -n</code> through that
fixed helper and fails closed instead of prompting. <code>agent-browser install doctor --json</code> reports the
installed helper's route desktop template as
<code>remoteViewPrivileges.helperDesktopSession</code> and raises
<code>remote_view_route_desktop_helper_stale</code> when that helper still
starts a terminal-first route desktop.

The <code>v0.28.0</code> release-candidate lane adds
<code>agent-browser install workstation</code>. It plans or installs the
binary, versioned support manifest, pinned local Guacamole Compose stack and
schema, protected generated PostgreSQL and route credentials, dashboard
service, runtime interlock, and PostgreSQL backup units without a source
checkout or pnpm reference:

```bash
agent-browser install workstation --dry-run --json
agent-browser install workstation --apply --json
agent-browser install workstation --dry-run --runtime-replacement-policy full-shutdown --json
agent-browser install workstation status --json
agent-browser install workstation recover --transaction-id upgrade-... --json
agent-browser install workstation finalize --json
agent-browser install workstation gc --dry-run --json
agent-browser install transactions list --json
agent-browser install transactions inspect --transaction-id upgrade-... --json
```

Every dry-run includes <code>serviceStateMigrationPreview</code>. It reads the
current Service State without writing and reports exact added, changed, and
removed IDs by record class, candidate-led browser contamination findings,
preserved unknown fields, recovery-artifact compatibility, and the paths that
apply would use. Dry-run creates neither a backup nor a migration receipt.
Apply stages the same migration only after candidate preflight and a stable
runtime census. It then records the exact backup locator, restore procedure,
before and after digests, summary, contamination report, and terminal migration
receipt in the private transaction artifacts. The default migration never
deletes profiles, browsers, sessions, displays, routes, leases, handoffs,
principals, capabilities, runtime owners, or lifecycle identities. Unknown
successor fields and action types are preserved without effect authority, so
rollback readers retain newer terminal bookkeeping. An already advertised
recovery action does not require an upgrade merely to apply it.

Cooperative continuity is the default runtime replacement policy. When an old
managed runtime cannot complete handoff, run a dry-run with
<code>--runtime-replacement-policy full-shutdown</code> and review the returned
<code>runtimeReplacementPlan</code>. It identifies the exact managed session
lanes and source process, states that live browser state will end, confirms
profile preservation, and supplies a <code>planDigest</code>. Apply requires the
same digest through
<code>--expected-runtime-replacement-plan-digest &lt;sha256&gt;</code>. The
transaction closes only those reviewed lanes, preserves the profile directory
and stored credentials, proves a stable browserless census, retires only the
recorded source process identity, and starts the candidate generation. Open
tabs and in-memory state are lost. After the first close receipt, recovery is
forward-only through transaction inspect and resume or recover. External,
manual-preservation, ambiguous, and unproven processes remain untouched.

The first apply uses one <code>sudo -v</code> authorization boundary for host
preparation. Before authorization or payload staging, real-host preflight
requires at least 6 GiB of free disk capacity. JSON output exposes
<code>hostPlan.availableDiskBytes</code>, <code>minimumDiskBytes</code>, and
<code>diskSpaceReady</code>. Fresh install and upgrade share one durable
transaction engine. Real-host apply records two matching read-only runtime
census rounds before stopping user units or staging a candidate. The
census joins service state, runtime-profile state, named supervisors, daemon
and process-instance evidence, bounded CDP browser and target digests,
displays, routes, streams, and durable handoffs. Missing, changing, or
conflicting evidence fails closed without replacing the selected generation.
Successful JSON output exposes <code>runtimeCensusTransaction</code>, the private
receipt under
<code>~/.agent-browser/runtime-adoption/transactions/</code> that contains the
census digest and per-runtime classifications. Host prerequisites succeed
before admission drain or ownership transfer. On the first transactional
upgrade from the legacy mutable layout, the installer seals the exact existing
binary, support tree, and user units as the rollback generation before
replacing stable entrypoints with generation-backed links. It restores the
original files and selector if that conversion fails. Unit types introduced
after the legacy install remain inert until candidate selection. On Linux, the
installer repairs a daemon identity affected by this controlled relocation
only when its exact process start token and imported binary digest match. If a
census-proven browserless daemon does not finish graceful shutdown, the installer
force-stops only that exact verified daemon process after the bounded grace. For a
Linux idle daemon whose executable was replaced after launch, the installer repairs
the deleted proc-executable identity only when the PID, start token, original path,
and recorded executable digest match the live inode exactly. For a
schema-v1 live daemon with no owner record, exact census evidence permits the
candidate to create the first receipted owner only after daemon revocation.
Historical route, display, and stream identifiers are scoped to their browser
owner so provider reuse cannot merge unrelated runtime candidates. Verified
orphan adoption maps process-observed Chrome, Chromium, Brave, and Edge family
labels to the canonical <code>chrome</code> engine while continuing to reject
Lightpanda and unrelated family evidence. Its temporary candidate session is
scoped to the upgrade transaction, so a retry cannot reuse a candidate daemon
left by an earlier failed transaction. If persisted browser health or tab
validity lags a retained live browser after rollback, upgrade bootstrap performs
one read-only loopback CDP observation. It accepts that evidence only when the
recorded PID and process identity, unique ready owner, active session, process
digest, and exact target all still match. The observation does not repair
Service State or launch another browser. If service projection metadata omits the
runtime-profile name, orphan adoption recovers it only from one runtime-state
record with the same exact process identity and DevTools browser endpoint. Zero
or multiple matches fail closed. Cooperative
and verified orphan browsers move through receipt-bearing owner generations;
manual and external
browsers remain preserved without effect authority. The same atomic
service-state transaction commits effect authority to
<code>~/.agent-browser/service/runtime-owner-registry.json</code>. New
generations merge that durable registry on every read, so a legacy dashboard
or daemon that rewrites <code>state.json</code> cannot erase candidate ownership
during the shadow interval. The selector changes only
after every discovered runtime has a proven disposition. Verified live
browsers without a session route remain preserve-only because
orphan resume has no safe source session to bind. After acceptance, install
and remote-view doctors retain an exact session with ledger disposition
<code>manual_preservation</code> as the nonblocking
<code>active_runtime_manual_preservation</code> warning until its operator
closes it. If an exact
old-generation daemon reports that the cooperative handoff command is
unavailable, apply verifies its recorded executable identity, revokes only
that daemon's effect authority, advances the exact registry owner to an
orphaned generation, and sends the retained browser through the same process,
profile, endpoint, target, and logical-identity checks used for orphan
adoption. It does not signal the browser process. A later rollback records
operator recovery required because the old daemon cannot be restored
automatically. If preparation adds the <code>agent-browser</code> or
<code>docker</code> group to the current user, the command exits with status 75
and a <code>relogin_required</code> JSON state. Log out and back in or reboot,
then rerun the same apply command. With both groups effective, apply starts the
pinned stack, creates the two route users and canonical Guacamole rows, opens
distinct XRDP displays selected by readiness, projects
<code>guacamole:1</code> and <code>guacamole:2</code> into service state, and
activates the user services only after the final doctors pass.
The Guacamole web container loads the packaged agent-browser defaults
extension. It performs a one-time browser-origin migration to the
<code>text</code> input method, making text input the default for existing and
new connections while preserving later user overrides.
The packaged container entrypoint copies the sealed extension template into
container-local writable storage before Guacamole generates its authentication
extensions. The immutable host generation remains read-only.
Host preparation includes <code>x11-utils</code>, ImageMagick, Tesseract, and
a path-scoped AppArmor policy that permits managed Chrome to create the user
namespace required by its sandbox on Ubuntu 24.04. The policy is required only
when the kernel enables AppArmor and restricts unprivileged user namespaces;
an AppArmor-disabled WSL kernel reports it as not required. The installer does
not disable the host restriction or add <code>--no-sandbox</code>. Final readiness
recognizes the pinned Compose Guacd container and the Chrome binary in
agent-browser's managed browser directory. Remote-view doctor reports the
managed Chrome sandbox policy separately and refuses live-gate readiness when
that policy is absent, inactive, or does not match the managed browser path.
Standalone doctor runs discover their helper scripts from the installed
versioned support root, so no checkout or ambient script-root override is
required.

Before a real-host upgrade enters effects, dry-run reports
<code>candidatePresentationPrerequisite</code> with
<code>proofPhase=bootstrap</code>. It is ready when one opaque durable handoff
identifies an exact healthy browser process, target, and unique current owner
session that the staged candidate can adopt. A ready route, display, or
old-generation presentation receipt is not required at bootstrap because the
candidate must reacquire and prove those replaceable resources. Apply records
a terminal zero-effect preflight block when no adoptable handoff exists. Fresh
installs and isolated development installs are exempt. Structured handoffs
never fall back to stale session labels when current owner evidence is missing.

On real-host apply, the installer starts the candidate dashboard backend on
the second port after stable ingress and stages it before admission drain.
The shadow remains backend-only while every old-generation cooperative lane
completes handoff prepare. A no-browser `stream status` bootstrap starts the
transaction runtime host only after that batch finishes, preventing cross-generation
Service State lock contention. After runtime transfer reaches candidate readiness, apply waits up to five
minutes for an authenticated candidate journey. Resolving an opaque durable
handoff to a ready operator surface through the staged candidate automatically
commits that exact generation. The commit rechecks the candidate-bound receipt
against the current runtime owner, route, display, target, provider, and
deployment generation. If proof is not established before the deadline, the
installer rolls back the staged candidate and preserves the selected installed
generation. <code>agent-browser dashboard ingress commit
--expected-revision &lt;revision&gt; --handoff-id &lt;id&gt;</code> remains an explicit
recovery command for a ready receipt recorded before automatic selection
completed. The file-based evidence form
remains available for externally receipted integrations. Stable ingress
continues serving the selected backend while proof is pending. Reconciliation
then quiesces only the generation backend, runtime interlock, and backup timer,
starts the managed candidate backend on the next port, atomically selects it,
and stops the shadow process. If reconciliation fails, it restores every
installed unit and authenticated ingress receipt to its exact prior state and
writes a private diagnostic receipt to
<code>~/.agent-browser/convergence/workstation-last-failure.json</code>.
Duplicate-profile pressure and executable drift in an inactive optional
session supervisor remain visible as install-doctor advisories without
failing workstation route reconciliation. Active supervisor drift remains
blocking.
Before Compose can recreate Guacamole, reconciliation compares the protected
PostgreSQL password with any retained database container. If they differ, it
updates only the protected password entry, keeps the file private, and leaves
the database unchanged. It also reuses the retained Compose project label so
the existing containers are reconciled in place. A retained container without
a usable password or project label fails closed.

Use <code>agent-browser install workstation reconcile --json</code> to run the
same lightweight maintenance authority as the installed timer. It reconciles
route users through the non-PAM helper, applies only identity-proven unattended
process and profile cleanup, finalizes eligible retention, and removes
unreferenced sealed generations. It does not reinstall Chrome, recreate
Guacamole, quiesce user units, or restart the dashboard. Repeated failures use
bounded backoff and become a typed incident on the third consecutive failure.
Ambiguous and reviewable resources remain untouched. Workstation installation
also selects one runtime host for every ordinary named session. Current
binaries retain legacy socket connectivity for explicit handoff but reject new
per-session daemon creation. If no host is selected, rerun
<code>agent-browser install workstation --apply --json</code>. The authenticated
dashboard summarizes multiplicity, protected, reclaimable, and unowned RSS,
cleanup obligations, retention results, monitor freshness, and blocking
reconciliation incidents from the same receipts. Use
<code>agent-browser install workstation backup --json</code> for the same
protected PostgreSQL backup operation invoked by the installed timer. Use
<code>agent-browser install workstation status --json</code> for a redacted
selected-generation, migration, blocker, admission, and terminal-state view.
Legacy migration materializes a persistent placeholder profile only for an
inert session with no principal, work capability, browser, or tab. The
placeholder restores referential identity without granting authority. An
effect-bearing missing-profile reference still blocks before commit.
A stale tab whose retained handle is already invalid with
<code>browser_missing</code> may be preserved through an inert
<code>not_started</code> browser placeholder and released system-session
placeholder only when no principal, work lease, process identity, runtime owner,
or existing session binding exists.
Terminal orphaned or released remote-view evidence may use the same inert
placeholders when any retained process identity is confirmed absent and no
active viewer, controller lease, or existing session binding remains. A
historical controller epoch does not count as current controller authority
after the controller lease is absent. A
registered principal binding at or behind the unique retained owner generation
stays non-effect-capable reconciliation evidence until a live exact process is
established. A unique unbound legacy owner remains historical identity.
Effect-bearing references still block.
When a live selected runtime host predates boot-epoch persistence or belongs to
a prior boot, guarded apply re-observes its exact process, socket, generation,
and binary and CAS-refreshes only that same selected ingress identity before
candidate staging. Ambiguous or changed identity still blocks.
If a rollback reports <code>operator_recovery_required</code>, run
<code>agent-browser install workstation recover --transaction-id &lt;id&gt;
--json</code> with the exact admission-owning transaction ID from the failure.
Recovery fails closed unless the sealed old generation is selected, no
candidate executable is live, no candidate dashboard route remains, and a
fresh two-round runtime census is stable. It preserves the transaction ledger,
appends a recovery checkpoint, and only then reopens runtime admission.
Install transaction discovery is read-only:

```bash
agent-browser install transactions list --json
agent-browser install transactions inspect --transaction-id upgrade-... --json
```

Guarded resume, rollback, and close require the exact transaction ID, current
revision, immutable candidate generation, and recorded census digest returned
as <code>runtimeCensusDigest</code> by inspect. Pass <code>none</code> when the
field is null:

```bash
agent-browser install transactions rollback --transaction-id upgrade-... --expected-revision 7 --candidate-generation 0.28.0-... --census-digest &lt;sha256&gt; --json
```

Any compare-and-swap mismatch is zero-effect and requires a fresh inspect.
Close is available only for a proven zero-effect terminal transaction. There
is a mixed-version compatibility boundary: the durable enum remains an
older-reader-compatible failed terminal state, while
<code>terminalResult: closed_zero_effect</code> carries the precise outcome.
Current list and inspect output classify that combination as terminal
zero-effect history. A legacy <code>closed_zero_effect</code> enum advertises
one exact guarded <code>close</code> action to normalize the record. There
is no inferred latest mutation or broad force unlock. A post-commit rollback
restores the exact state snapshot and previous generation selector or records
typed operator recovery with rollback evidence retained.
The <code>readiness</code> object separates
<code>payloadReady</code>, <code>selectedGenerationReady</code>,
<code>runtimeConvergenceReady</code>,
<code>upgradeTransactionState</code>,
<code>dashboardIngressReady</code>, <code>operatorJourneyReady</code>, and
<code>rollbackReady</code>. Overall <code>ready</code> remains false while a
transaction or admission drain is active or any axis is unproved. Accepted
generations keep rollback authority for 24 hours.
Use <code>agent-browser install workstation gc --dry-run --json</code> to
preview reviewed old-generation cleanup. Apply retains the selected generation
and the immediately previous healthy rollback generation. It also retains
exact live-process, supervisor, active-transaction, and open-rollback
references. Eligible accepted transactions are finalized automatically while
their durable metadata remains available for audit.

<code>agent-browser install doctor --json</code> verifies the installed
binary, controller assets, Guacamole manifest, and Guacamole files against the
SHA-256 provenance recorded during workstation installation.

This release-candidate branch remains a release no-go until its disposable
Ubuntu install, reboot, restore, full CI, and release-artifact gates pass.

For a persistent local dashboard and self-healing RDP route plane, run
<code>bash scripts/install-dashboard-user-service.sh</code> from the checkout.
Alongside <code>agent-browser-dashboard.service</code>, it installs
<code>agent-browser-runtime-interlock.timer</code>. The interlock runs after
boot and five minutes after each completed pass by default. It invokes the
installed lightweight workstation reconciler directly, reconciles route users
through the non-PAM helper, applies only identity-proven unattended cleanup,
advances retention, and records bounded backoff under
<code>~/.agent-browser/convergence/runtime-monitor.json</code>. It does not
require a checkout or pnpm. Set
<code>AGENT_BROWSER_RUNTIME_INTERLOCK_INTERVAL</code> before installation to a
systemd duration such as <code>5min</code> to change the cadence.

During development, run <code>pnpm publish:local-dashboard</code> to rebuild
the dashboard and candidate executable. The publisher is a thin client of the
canonical workstation transaction: closed-world census, admission drain,
receipt-bearing owner transfer, selector commit, rollback, and dashboard
reconciliation remain installer-owned. It never directly replaces the stable
binary or maintains a second socket-only handoff algorithm.

## Stealth CDP Chromium

Use <code>agent-browser install stealthcdp-chromium</code> to install the
preferred patched Chromium release when the public
<code>CochranResearchGroup/chromium-stealthcdp</code> Windows asset is
available. The installer verifies the release archive and
<code>chrome.exe</code> hashes, places the artifact under
<code>%LOCALAPPDATA%\chromium-stealthcdp</code> on Windows or the matching
WSL-mounted <code>AppData/Local</code> directory, and exposes
<code>current/manifest.json</code> plus <code>current/chrome.exe</code>.
Set <code>AGENT_BROWSER_STEALTHCDP_CHROMIUM_INSTALL_ROOT</code> only when that
location must be overridden.

agent-browser auto-discovers that stable manifest path when it exists, but it
only prefers <code>stealthcdp_chromium</code> automatically after the manifest
has live smoke evidence showing <code>navigator.webdriver</code> is false.
Run <code>agent-browser install doctor</code> to inspect the no-launch
readiness view. On Linux, its JSON also reports
<code>remoteViewPrivileges</code> with helper, sudoers, group, membership,
route desktop template readiness, and <code>requiresInteractiveSudo</code>
fields for the Guacamole/RDP path, plus <code>service</code> readiness from a
no-launch service-status probe. The <code>runtimeMultiplicity</code> object is a
read-only census of dashboard processes, runtime hosts, legacy per-session
daemons, executable generations, and any active convergence window. A drift
report does not authorize cleanup by itself. During a bounded upgrade, each
accepted runtime host must match its recorded PID, process start token, binary
hash, generation, and socket identity.

The authenticated runtime-health and Service Status responses project the same
<code>runtimeLifecycle</code> contract. It distinguishes steady state from a
transaction-bound convergence window and reports lifecycle ownership,
reconciliation freshness, retention effects, protected versus reclaimable
resource pressure, cleanup obligations, and blocking incidents. Recovery starts
with <code>agent-browser install doctor --json</code> and
<code>agent-browser --json service status</code>. Do not kill an authenticated
browser or delete a profile from process-list evidence alone. Let a bounded
transaction roll back, preserve ambiguous resources, and use reviewed GC only
for an exact eligible plan.

When WSL launches the installed Windows <code>chrome.exe</code>, agent-browser
translates mounted Windows paths such as <code>/mnt/c/...</code> to
<code>C:\...</code> for Chrome arguments and adds <code>--no-sandbox</code>.
This host mode needs that launch posture for the patched Windows build to
expose DevTools reliably.

Run <code>agent-browser doctor windows-browser</code> to diagnose the WSL to
Windows browser route without changing firewall, <code>.wslconfig</code>, SSH,
or profile state. The doctor reports WSL mode, the Windows host IP used for NAT
fallback, candidate CDP endpoints, fixed-port probe results, stable manifest
visibility, and whether WSL path translation plus <code>--no-sandbox</code>
apply for the selected Windows browser.
Add <code>--scan-ports --firewall</code> to run a bounded scan of common
browser/debug ports plus localhost listeners and query Windows firewall plus
Hyper-V firewall state through PowerShell when available. This remains
read-only. The doctor also reports <code>profileSmoke.available</code>,
<code>profileSmoke.command</code>, and <code>profileSmoke.reason</code> so
operators can tell whether the Windows <code>chromium-stealthcdp</code>
profile-write smoke is ready to run.

Run <code>agent-browser doctor remote-view</code> before changing Guacamole or
RDP setup. It is read-only and reports install state, Guacamole route-pool
readiness, XRDP policy, existing <code>agent-browser-rdp</code> and
route-specific user inventory, one-time privileged helper readiness,
remote-view config file presence with keys only, route-display state,
agent display access to those XRDP displays, stable issue codes with
remediation text, drift findings, and the next setup action.
Child diagnostic timeouts use distinct <code>*_timed_out</code> issue codes and
do not prove install or readiness drift. Run the reported direct helper command
for an inconclusive timeout. A completed missing-route-display result remains
the primary remediation when another embedded helper times out.

When WSL launches a Windows <code>chrome.exe</code>, agent-browser translates
mounted Windows paths in Chrome arguments from <code>/mnt/&lt;drive&gt;/...</code>
to Windows form before launch. This covers profile, cache, download, extension,
and positional path arguments, preventing Windows Chromium from treating WSL
paths as literal Windows directories.

Run <code>agent-browser setup windows-browser --print-powershell</code> to
print a reviewed Windows PowerShell setup helper for mirrored WSL networking,
scoped Hyper-V firewall rules, fixed CDP ports, SSH tunnel fallback, and
rollback commands. The agent-browser command is preview-only and does not
mutate system state. The generated script is dry-run by default and requires
its own <code>-Apply</code> switch before it creates a scoped firewall rule.
Add <code>--doctor</code> to embed current route diagnostics as PowerShell
comments and infer <code>nat</code> mode when mirrored networking is not active
and <code>--mode</code> was not supplied. The generated script reminds
operators to run the profile smoke when doctor reports it is available.
When the Windows SSM debug instance has been provisioned, run
<code>pnpm test:windows-browser-setup-powershell-live</code> to verify that the
generated setup script parses on Windows, stays dry-run by default, prints
rollback commands, and does not report creating firewall rules.
On WSL hosts with the Windows <code>chromium-stealthcdp</code> artifact
installed, run <code>pnpm test:wsl-windows-chromium-profile-live</code> to
verify the headed agent-browser launch path with a Windows-mounted profile. The
smoke uses an isolated daemon socket, expects profile files to be written,
checks Chrome stderr for <code>/mnt/...</code> path or write-failure evidence,
and closes the test browser.

## Updating

Upgrade to the latest version:

```bash
agent-browser upgrade
```

For this fork, prefer replacing the binary from the latest GitHub release. The
legacy `upgrade` command may still know about upstream package-manager installs,
but those channels are not authoritative here.

Run <code>agent-browser install doctor</code> after replacing the user-scoped
binary or changing a custom browser manifest. It does not launch Chrome. The
doctor checks the command on <code>PATH</code>, the running executable, the pnpm
global package binary when pnpm is available, the current workspace binary when
run from a checkout, and launch readiness for configured custom browser builds.

## Maintainer release validation

Before creating a release, maintainers can manually run the <code>Release</code>
GitHub Actions workflow with <code>dry_run</code> set to <code>true</code>. The
dry run builds all platform binaries, verifies expected artifacts, and skips
GitHub release creation.

After installing or replacing a release candidate binary locally, run
<code>agent-browser install doctor</code>. Treat any nonzero result as an
install drift or custom browser readiness issue before calling the candidate
validated.

Release diagnostics must also require <code>runtimeLifecycle.ready=true</code>,
steady multiplicity after any convergence window closes, a fresh reconciliation
receipt, no missing cleanup obligation, no blocking repeated-failure incident,
and no unexplained retained generation. The disk set may contain the selected
generation plus one healthy rollback generation inside its retention window.

## Custom browser

Use a custom browser executable instead of bundled Chromium:

- **Serverless** - Use `@sparticuz/chromium` (~50MB vs ~684MB)
- **System browser** - Use existing Chrome installation
- **Custom builds** - Use modified browser builds

```bash
# Via flag
agent-browser --executable-path /path/to/chromium open example.com

# Via environment variable
AGENT_BROWSER_EXECUTABLE_PATH=/path/to/chromium agent-browser open example.com
```

### Serverless example

Use `@sparticuz/chromium` or similar to obtain a Chromium executable path, then pass it via `--executable-path` or `AGENT_BROWSER_EXECUTABLE_PATH`.

Install the skill from the repository copy used by your agent environment.

This works with Claude Code, Codex, Cursor, Gemini CLI, GitHub Copilot, Goose, OpenCode, and Windsurf. The skill is fetched from the repository and stays up to date automatically.

> **Do not** copy `SKILL.md` from `node_modules` -- it will become stale as new features are added. Always use `npx skills add` or reference the repository version.

### AGENTS.md / CLAUDE.md

Add to your instructions file:

```markdown
## Browser Automation

Use `agent-browser` for web automation. Run `agent-browser --help` for all commands.

Core workflow:
1. `agent-browser open <url>` - Navigate to page
2. `agent-browser snapshot -i` - Get interactive elements with refs (@e1, @e2)
3. `agent-browser click @e1` / `fill @e2 "text"` - Interact using refs
4. Re-snapshot after page changes
```
