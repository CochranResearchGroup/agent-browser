# Service Mode

## Hosted reconnect, rules and artifacts

The connected MCP catalog has 16 workflow tools. Discover actual schemas before
use; the source guide does not prove installed support.

`browser_reconnect` accepts taskId and operation status, disconnect, reconnect,
rebind, configure or reopen. All changes require requestId and expectedRevision
from current status. configure requires lossPolicy report_only or reopen; rebind
requires desktop with desktopId/generation. Status is metadata-only; reconnect
freshly verifies the retained process and Native assignment without launch.
BrowserUnreachable, positively absent BrowserLost and RebindRequired are distinct.
recoveryDesktop is nullable approved recovery intent. Default loss policy reports loss. Explicit reopen requires opt-in and no pending
uncertain effects: managed browsers reopen empty/blank without replaying history;
borrowed browsers require the app's fresh attachment and desktop proof and never
launch an app browser. Human control remains held. Results include reconnect
revision/state/lossPolicy/lastRequestId/observedDesktop/pending/automaticReplay:false.


When the original managed process is positively absent, explicit rebind may retain
an exact current ready desktop as approved recoveryDesktop. State stays
browser_lost: this records a future recovery destination, not a physical move,
connection or rewrite of the old browser binding. A subsequent explicit reopen
under lossPolicy reopen requires agent ownership and no pending effects. Only a
verified replacement on that approved target publishes its new physical binding
and clears recoveryDesktop. Live managed generation-changing rebind remains
capability-refused. PID-reuse absence is conservatively blocked. Borrowed reopen
still requires fresh app attachment/desktop proof and preserves any human hold.
This source contract's new recovery path still needs native custody qualification.

```bash
agent-browser --json mcp host-reconnect TASK status
agent-browser --json mcp host-reconnect TASK configure '{"requestId":"loss-policy-1","expectedRevision":0,"lossPolicy":"report_only"}'
```

`browser_policy` takes taskId and operation status, set_app, set_task, clear_app,
clear_task or override. Mutations require expectedRevision, actor and reason.
Policy version 1 contains deniedActions and artifactDestinations mapping a handle
to an absolute canonical existing directory. A task policy completely replaces
app defaults; clear_task restores them. Optional browser_open taskPolicy
uses that same v1 shape to bind an explicit task override before launch. Unrestricted tasks require no extra grant.
Scoped overrideAction/requestId returns overrideId for policyOverrideId on that
exact task/action/request/current policy, never to bypass human control or peers.
Pass policyOverrideId and requestId at the top level of the supported page tool
or browser_command; for example action fill with params selector/value.

`browser_artifact` takes taskId, kind screenshot/download, handle and relative
name; download requires selector. Optional fullPage, requestId and policyOverrideId
follow discovery. It writes only to the authorized local handle, refusing path
traversal, symlinked destinations and existing files. Results contain local
artifactId/path/handle/name/result and publication not_requested. Publication and
private-content review remain separate from capture. Rules cover supported
routes, not unmanaged CDP or semantic website restrictions.

browser_close defaults to scope task. Explicit scope browser requires actor and
reason and refuses app-borrowed browsers or any peer task. Its supported managed
close reports fresh OS absence of the original process; full child-process residue
requires independent census. Refused or uncertain close never authorizes replay.

These contracts preserve the original app session, durable handoff and Native
viewer. Physical same-process relocation remains a provider gap tracked by
Remote View #578; metadata rebind is not a physical move. Keep the original browser
rather than substituting another profile or reopening it to simulate relocation.


## Resource budgets and durable completed history

New browser process admission reserves 5% of total RAM, with a 1 GiB minimum.
Under memory pressure, new task acquisition runs the existing owner reaper for
eligible idle work, then waits up to five seconds. Existing task/profile
continuation stays protected. The supervisor uses a soft threshold of 25% RAM
and has no default hard cap that terminates ongoing work.

Set overrides before workstation installation or host startup. Installation
captures explicit settings into the host unit. Shell changes do not alter a
running host. Service Status reports the reserve/source and archive counts under
<code>browserRuntime.storage.terminalHistory</code>.

Older completed session/tab evidence moves atomically into the existing SQLite
archive. It has no automatic expiry. Handoff references retain target evidence
beyond the recent-record budget. Live records and link/tab lifetimes are unchanged.

```bash
agent-browser runtime history sessions 100 --json
agent-browser runtime history tabs 100 --json
agent-browser runtime history sessions 100 42 --json
```

The last argument is <code>data.nextCursor</code> from the preceding page. Pages
are newest-first, with a maximum of 1000 records. This command reads an existing
database without migration, state creation or launch.

## MCP browser tasks

If `browser_open` is absent from the client's callable tools, configure its MCP
integration with the installed `agent-browser mcp serve` stdio command and
reconnect to refresh the catalog. Continue through the installed CLI while
fixing integration. Verify actual client exposure separately from a direct
server listing.

Codex MCP configuration:

```toml
[mcp_servers.agent-browser]
command = "agent-browser"
args = ["mcp", "serve"]
```

Pin the reviewed absolute installed path for candidate qualification. Reconnect
after an executable or catalog update. Server configuration owns runtime and
public-origin settings; task callers use the workflow arguments.

Unknown command help fails with a concise typed error. Use `agent-browser runtime create --help` for focused profile creation guidance. Runtime creation returns a top-level record (`created`, `userDataDir`); workflow MCP text payloads use `success`, `data`, and `error`; JSON CLI failures use `success: false`, `error`, and `type`.

Call `browser_open` with a named `profile`, `profileMode: "persistent"`, a stable `taskKey`, and `url`. The operation creates or reuses that profile and opens one independent task tab. Its MCP text result contains `success`, `data`, and `error`; `data.taskId` targets subsequent page actions and `browser_close`.

Replay the same task key to return its current page and preserve edits without navigating again. Different task keys share a healthy same-profile browser through separate tabs. Closing one task preserves its peers and persistent profile data. Existing borrowed browsers remain open after the final task ends.

Select `profileMode: "existing"` to require an already registered profile. For temporary work, select `profileMode: "disposable"` and omit `profile`.

Call `browser_handoff` with `taskId` for a complete authenticated HTTPS `handoffUrl`. The MCP server uses `AGENT_BROWSER_PUBLIC_ORIGIN`, this Agent Browser service's public origin, to complete the owner's durable link. `AGENT_BROWSER_REMOTE_VIEW_PUBLIC_ORIGIN` separately locates the native desktop viewer. Operators configure these origins; task callers receive the complete link. A missing service origin returns `remote_view_public_origin_missing` in JSON-RPC `error.data.message` with configuration guidance. Handoff preserves the task and current page for subsequent page actions.

The handoff URL resolves the current owned desktop and redirects to native Remote View authentication without a Dashboard login. Opening this public link performs no browser recovery. Ask the task owner to check readiness if the desktop is unavailable.

After human assistance, call `browser_continue` with the same `taskId` to obtain its current profile, browser, tab and URL. Continuation observes the current page without navigating or creating another task. Subsequent page actions use that same task ID.

For a CDP-free sign-in task, call `browser_open` with `mode: "manual_login"`, a
named persistent profile, and the login URL. For example:

```json
{"profile":"canvacli","profileMode":"persistent","mode":"manual_login","taskKey":"google-login","url":"https://accounts.google.com/","serviceName":"canvacli","agentName":"codex","taskName":"Google sign-in"}
```

This opens a headed window on the configured native Remote View desktop without
CDP, a debugging port, or a debugging pipe. The same call returns `handoffUrl`
and requires `operatorVisible.state: "ready"`. Reuse the task key to retain the
login window. DOM/CDP actions and additional agent tabs are unavailable in this
mode. Authorized agents can instead use `native_capture` and `native_input`
through the existing Native owner when its current capabilities are ready.
Human takeover remains separate; these commands never return human control
automatically. The reported URL is the initial requested location
(`urlObserved: false`); desktop readiness and profile continuity do not verify
authentication.
To change debugging posture, discover `mode_convert` and review its explicit
replacement choices. A successful replacement preserves the logical task,
profile and original handoff while replacing the physical browser; unsaved page
state may be lost. Alternatively, explicitly close the task and reopen the same
profile in `automation` mode. Ordinary open never silently closes, replaces or
attaches to a browser in the other mode. Source/synthetic checks do not establish
installed Native readiness or authenticated site state.

The default MCP catalog contains 16 workflow tools: `browser_open`, `browser_navigate`,
`browser_snapshot`, `browser_click`, `browser_fill`, `browser_screenshot`, `browser_tab`,
`browser_handoff`, `browser_continue`, `browser_close`, `browser_control`, `browser_reconnect`, `browser_policy`,
`browser_artifact`, `browser_command` and `browser_discover`.
Page actions require `taskId`. Use `browser_tab` to list, create, select or close this
task's tabs; repeat a stable `tabKey` when retrying creation. Peer tabs stay outside
this scope. Use `browser_discover` for one advanced operation's argument schema,
then `browser_command` with `taskId`, `action` and page arguments in `params`.
Diagnostic and administrative discovery points to supported CLI/API operations.
Retired lease, recovery, repair and reset MCP tools are unavailable, including
through advanced dispatch. There is no legacy catalog mode. Contract metadata reports `mcpCatalog` and each named adapter's `mcp.available`; retained CLI/API contract names do not imply callable MCP tools.


Service mode turns agent-browser from a single CLI session helper into a persistent browser control plane. It keeps service-owned state for profiles, sessions, browsers, tabs, jobs, incidents, events, site policies, providers, and challenges so multiple agents and software clients can share browser automation without racing each other.

Profile ACL admission denials preserve `profile_access_denied` on the
`profile_access` axis with `no_effect`. The response includes the planner's
`profileAccessDecision`, subject and identity assurance, missing permission, and policy
revision; its recovery action is to inspect Profile access policy. Use the
same credential when following that read-only action. Do not change caller
labels, seed a profile, or retry a denied operation to bypass its policy.
Pre-dispatch denials have no job; join their request ID to the failure journal.
An oversized decision is explicitly marked
`profileAccessDecisionOmitted: record_size_limit` in journal details.


Dashboard fetch-failure elapsedMs measures time until fetch resolves or rejects; delayed journal delivery does not inflate it. The client rounds the wire value to nonnegative whole milliseconds so the integer-only receiver accepts high-resolution browser timings.
The primary connection batches image acknowledgements and checks fresh ownership before each write. Slow ownership reads run off the dashboard asynchronous workers so they do not block unrelated requests.

## Forensic failure journal

MCP `service_request` routes a handle-only browser operation using the returned
`serviceTabHandle.sessionName` or its session-prefixed `browserId`. Keep the
original handle; there is no need to duplicate its route fields. Explicit route
selectors remain subject to conflict and ownership checks.

MCP daemon-backed tool results preserve the daemon's `id`, `failure`, and
`terminalOutcome` when present. Use `terminalOutcome.provenance.requestId` and
`jobId` to correlate an ownership refusal with Service records; inspect the
structured failure recourse before retrying. Older responses may omit these
fields. The daemon request ID is distinct from the outer MCP JSON-RPC ID.

New service-generated connection IDs carry host lifetime evidence. After an
abrupt host exit, the original handle may reconnect when the service proves the
old host ended and the same subject still has permission. Live owners remain
exclusive. Legacy IDs, unreadable process evidence, and ambiguous PID namespaces
remain unresolved; matching labels alone never authorize takeover.

Local operators can preview `agent-browser --json service connections reconcile
--plan /absolute/plan.json`, then use `--apply` for the reviewed transition.
The plan uses `agent-browser.legacy-connection-reconciliation.v1` and contains
`statePath`, `custodySnapshotPath`, `custodySnapshotSha256`, `connectionId`, and
`expectedTabs`. Each expected tab records `browserId`, `targetId`,
`ownerSessionId`, and the complete `profileAccess`. Preserve the original
snapshot timestamp. Every current producer of that state root must be identified
through its exact process and systemd service and have started after the snapshot.
Changed custody or unknown producers refuse the operation. Apply uses the native
transaction store and returns an audit `eventId`; it changes only connection
state and derived handles. This Linux maintenance command is not available
through consumer HTTP or MCP service requests.

After a runtime-host interruption, bounded <code>evaluate</code>,
<code>probe</code>, and permitted <code>cdp_attach</code> requests can reuse the
original <code>serviceTabHandle</code>. The service validates child access,
runtime ownership, process identity, and endpoint identity before reconnecting
the exact retained target. It never creates a tab or substitutes a peer when
that target is missing. A <code>service_tab_recovery_*</code> failure includes
typed recourse to inspect the Service trace before retrying. Attachment failures
remain effect-uncertain because a CDP attachment may already have occurred.

Access-plan permission and occupancy denials take priority over freshness or
seeding advice. Follow the blocking policy or occupancy inspection action in
`decision.recommendedAction` and the exact `profileAccess.decision.nextAction`.

Authenticated service requests record the validated principal and its assurance
in job and terminal provenance, including profile policy mutations. Service,
agent, and task labels remain attribution and cannot replace that actor.

The runtime-host unit uses <code>KillMode=process</code> so host retirement does
not signal retained browser or display descendants. Browser and route cleanup
remain separate operations requiring their ownership checks.

The bounded Service event collection is for current operations, not complete
postmortem retention. Failed browser launches and non-success service jobs are
also appended to
<code>~/.agent-browser/service/failure-journal.jsonl</code>. Records carry a
typed category and code, occurrence time, runtime and boot epoch, safe causal
identifiers, and a bounded redacted summary. They exclude page content,
credentials, request headers, bearer material, raw operator URLs, raw durable
handoff IDs, and query strings. Private browser-launch records include a fixed <code>details.phase</code> label distinguishing validation, process/endpoint startup, protocol initialization, CDP connection, target discovery, active session and download policy. The label contains no raw error or private environment value. Unknown outcomes still require readback before another attempt.

Authenticated operators and software clients can read recent records with
<code>GET /api/service/failures?limit=100</code>. The reader skips malformed
lines and reports their count so one damaged occurrence does not hide later
evidence. Records enter private <code>failure-journal.pending/</code> files before
returning; Unix writes sync the file and directory entry. A bounded background
writer projects these records and recovers pending occurrences on daemon
startup without resubmitting requests. Journal lock contention defers
projection, while queue pressure preserves disk custody. Replay checks
occurrence identity and content before retiring pending files. Readback reports
<code>pendingRecordCount</code> separately from projected records and
process-local overload and failure counters. A persistence failure reports
<code>custody_failed</code>, not durable custody. Reads wait up to 250 ms for a concurrent journal writer, then report lock
contention if it persists. Power-loss and non-Unix directory durability require separate
platform validation. The authenticated
dashboard uses
<code>POST /api/service/failure-observation</code> for failures visible only in
the client, including Guacamole iframe failures, unusable handoffs, CDP streams
that deliver no frames, and dashboard transport failures. That intake accepts
only a strict allowlist and requires durable handoff identity to be hashed. The
dashboard retains up to 4,096 privacy-bounded same-origin status, resource, tab,
and runtime-health read failures per document and submits them after a later
valid recovery response. Any overflow is represented by an explicit delivery
gap occurrence.

The model is intentionally broader than the CLI. Agents usually interact through MCP, software projects usually interact through the HTTP API, and operators can inspect or intervene through the CLI and dashboard.

## Deterministic authentication runs

Service clients can restore a short-lived login without receiving credentials
or OTP material. Read <code>service_authentication_recipe_status</code> for the
repository recipe digest, then call
<code>service_authentication_run_start</code> with the exact retained
<code>serviceTabHandle</code>, profile, browser, session, organization, vault
account, challenge provider, and recipe digest. Use a unique operation ID for
each <code>resume</code>. Status and cancellation remain bound to the original
principal.

Each browser or challenge-provider effect enters durable pending custody before
execution. A process interruption therefore returns
<code>authentication_run_effect_outcome_unknown</code> and never repeats the
effect. For <code>bill-login-v1</code>, the IM Receipts watch must be live before
password submission can trigger SMS. The daemon accepts the provider only from
an HTTP loopback <code>IM_RECEIPTS_LOCAL_API_BASE_URL</code> and sends the
minimum-32-character <code>IM_RECEIPTS_SEALED_AUTH_CAPABILITY</code> only as a
bearer header. OTP material remains response-only and is excluded from MCP,
CLI, durable run state, and public status projections.

For <code>bill-login-v1</code>, only the exact signed-out Spend URL with title
<code>Page Not Found</code> invokes the recipe's fixed BILL login entry before
page classification. Other unsupported pages remain operator intervention and
are not redirected.

Static route-user setup accepts `AGENT_BROWSER_RDP_ROUTE_USER_POOL_JSON` as an arbitrary bounded JSON array. Each entry declares `id`, `connectionName`, and `routeUser`; `legacyConnectionName` is optional. Setup generates missing passwords into the user-scoped Guacamole secret file and preserves every configured route. When the array is absent, the legacy two-route environment is handled only by the compatibility adapter. The full `AGENT_BROWSER_RDP_ROUTE_POOL_JSON` emitted by inspection is canonical.

Service status includes `presentationCapacity` when durable presentation-slot authority is configured. The read-only projection reports arbitrary-size slot state counts, admitted and hard limits, human and recovery reserves, queued demand, oldest wait age, and redacted binding warnings. Reading it never launches a browser or opens a route. Logical CDP-only browsers remain separate from scarce operator-visible presentation capacity.

Service status also includes `desktopEvidencePolicy`, the redacted decision
contract shared by CLI, HTTP, MCP, generated clients, and the dashboard.

<code>p131-controlled-x11-v1</code> recipe. Service status reports

The normal request model is identity-first. A caller asks for a tab or browser action plus `serviceName`, `agentName`, `taskName`, and the target site or login identity. agent-browser selects or reuses the managed profile, manages any profile lease, queues browser-control work, and records the trace state. Direct profile selection is for known-login overrides and bring-your-own-profile workflows.

## What service mode provides

- A queued worker path for browser-control actions so concurrent clients are dispatched in order instead of competing directly for CDP.
- Persistent service records under the service state file, plus configured service records from `agent-browser.json` and `~/.agent-browser/config.json`.
- Trace context fields for `serviceName`, `agentName`, and `taskName`, so a service such as `JournalDownloader` can distinguish a task such as `probeACSwebsite`.
- Browser health detection for process exits, CDP disconnects, unreachable endpoints, target discovery failures, shutdown failures, and successful recovery.
- Operator remedies for job cancellation, incident acknowledgement or resolution, browser retry overrides, service reconciliation, polite browser close, and forced kill fallback.
- API and MCP parity for service records and typed browser-control actions.

Current automation control is CDP-first, but some services are sensitive to the
existence of a remote debugging port. The CDP-free operating mode keeps
agent-browser ownership of the headed browser process, profile lease, task
labels, process health, lifecycle, and operator handoff. P110 PoC 1 adds
service-bound desktop capture, and PoC 2 adds registered deterministic location
over that capture. PoC 4 adds a repository-fixture-only prompt observation
contract. These observation slices add neither CDP nor an input effect.

## Capture a service-owned desktop frame

Capture one fresh PNG from the full operating-system desktop that contains an
existing service-owned browser. This observation path can see
browser-external prompts that the Chrome DevTools Protocol (CDP) page
`screenshot` command cannot see.

> **Experimental:** P110 PoC 1 is source-only. It has no live RDP or Guacamole
> acceptance and does not prove that an installed runtime contains the feature.

The service resolves `browserId` to one exact nonterminal browser, ready view
stream, ready route, and display allocation. The request cannot supply a
display name, route URL, Guacamole URL, provider URL, Xauthority path, output
path, crop, or input option. This keeps display authority in retained service
state instead of caller-controlled routing data.

Use the CLI for a direct queued capture:

```bash
agent-browser desktop capture --browser-id browser-123 --json
agent-browser desktop capture --browser-id browser-123 --max-bytes 8388608 --json
```

Use the canonical service request from HTTP:

```bash
curl -X POST "http://127.0.0.1:9223/api/service/request" \
  -H "content-type: application/json" \
  -d '{"action":"desktop_capture","browserId":"browser-123","format":"png","maxBytes":4194304,"serviceName":"DesktopObserver","agentName":"capture-agent","taskName":"capture-frame"}'
```

MCP clients can send the same fields through `service_request` or call the
dedicated `desktop_capture` tool. Software clients can call
`requestServiceDesktopCapture()` for the queued response or
`captureServiceDesktopFrame()` for the convenience form. Use
`createServiceDesktopCaptureRequest()` when you need to build the canonical
request without sending it:

```javascript
import { captureServiceDesktopFrame } from "@agent-browser/client/service-request";

const desktopFrame = await captureServiceDesktopFrame({
  baseUrl: "http://127.0.0.1:9223",
  browserId: "browser-123",
  maxBytes: 4 * 1024 * 1024,
  serviceName: "DesktopObserver",
  agentName: "capture-agent",
  taskName: "capture-frame",
});
// => { success: true, data: { context, frameReceipt, imageBase64 } }
```

prove that a specific retained browser has a ready route or capture provider.
Only a successful response for the requested `browserId` proves current
workspace readiness.

## Service clients

Failed service requests preserve the legacy <code>error</code> string and may
also include a versioned <code>failure</code> object. Software clients should
use <code>getServiceFailureRecourse()</code> or
<code>requireServiceRequestSuccess()</code> and branch on
<code>retryDisposition</code>. A
<code>service_state_lock_timeout</code> with
<code>effectState="effect_uncertain"</code> requires reading the exact job,
trace, and current resource state before another mutation. A lifecycle-owner
blocker requires one refreshed access plan. Reuse is allowed only when that
plan returns mutually consistent <code>browserId</code> and
<code>sessionName</code> hints. Do not blind-retry either failure or open a
duplicate profile lane.

Current <code>service status</code> responses also include
<code>serviceStateLockDiagnostics</code>. This bounded, process-local diagnostic
shows active lock holders, recent wait and hold phases, timeout counters, and
recovered process-lock poisoning. It contains no Service State paths or request
payloads, is never persisted, and does not grant retry permission.

An exclusive file-lock holder also publishes a bounded sidecar beside the
selected Service State file. A <code>service_state_lock_timeout</code> may append
a validated holder status, PID plus process-start identity, build generation,
operation, lock mode, current phase, and coarse state counts. Missing, stale,
corrupt, or racy evidence remains explicitly unknown or stale. Current holder
evidence also includes monotonic lock wait and elapsed-hold timing plus the
acquisition wall time. The sidecar
contains no URLs, profile paths, page data, credentials, or request payloads,
and the exact holder removes it before normal release. It is diagnostic only:
never force-unlock, terminate, take over, or retry from this evidence.

Retirement serializes through a separate exclusive retirement fence while
holding shared Service State admission. Job and access-plan snapshots remain
readable during external effects. Controller publication and handoff writes
remain fenced and return within their lock budget with the read-only command
<code>agent-browser service jobs --json</code>. Inspect the job and current
access plan before retrying; reconcile uncertain effects without replaying
them. The timeout distinguishes <code>holder_lock_scope=retirement_fence</code>
from <code>state_lock_mode=shared</code>. Unix holders report fresh same-boot
monotonic elapsed time; legacy holders and unsupported clocks report unknown
rather than a frozen sample. Recorded build generation remains separate from
the installed executable path.

The JSON repository prepares and serializes pure candidate state outside the
exclusive file lock, then revision-fences the short durable commit. It may
replay one stale in-memory mutation against a fresh snapshot. Browser, tab,
route, provider, and tenant effects must remain outside that closure and are
not retried. Unknown top-level fields round-trip without gaining authority.

/api/service/access-plan</code> and <code>POST /api/service/request</code>. MCP

<code>service_access_plan</code> and <code>service_request</code>. Generated

reuse its exact retained browser and session. Its first authenticated tab

principal and profile identity. The broker prepares that route before relay,
so an unrelated transport default session and its profile lease cannot capture
the request. Capability rotation does not change the route, and raw capability
material is never part of its name. A foreign principal waits, an
unauthenticated caller must authenticate, and contradictory same-principal
profile evidence returns a typed lifecycle identity inconsistency. Never place
the capability in a URL, request body, command-line argument, log, or persisted

## Protected lease authority bootstrap

<code>pnpm install:privileges -- --apply</code> includes the protected
lease-authority first bootstrap inside its single interactive sudo boundary. It
banks the exact reviewed Agent Browser binary by SHA-256, creates root-private
authority state, and installs and enables fixed systemd service and socket
units. From a source checkout, set
<code>AGENT_BROWSER_LEASE_AUTHORITY_BINARY_SOURCE</code> to the exact reviewed
release binary. The passwordless helper cannot sign, mutate, bootstrap, or
upgrade lease authority. A healthy rerun retains the selected installed
generation. It may restart the exact stopped socket, but it refuses modified
units, modified banked bytes, or invalid existing authority state. The service
uses <code>ProtectHome=read-only</code> so it can prove an enrolled user-owned
managed profile without modifying that profile. Its only filesystem capability
is <code>CAP_DAC_READ_SEARCH</code>, which permits canonical identity and
ownership checks through mode-<code>0700</code> operator directories without
granting writes. A healthy rerun has guarded migrations for the exact prior
no-capability unit and <code>ProtectHome=true</code> unit. Any other unit drift
remains an error. A rerun can also recover the exact
interrupted form of that migration when the unit points to any absent,
well-formed banked generation and exactly one valid retained generation is
proven, even when the retry uses a different candidate. It does not install
either candidate or repeat bootstrap.

Normal privilege-installer reruns retain an exact ready authority generation.
To replace it with an explicit reviewed candidate while preserving protected
state, set <code>AGENT_BROWSER_LEASE_AUTHORITY_BINARY_SOURCE</code> and run
<code>pnpm install:privileges -- --apply --upgrade-lease-authority</code>. The
upgrade banks the candidate immutably and switches only the exact ready service
unit.

Clients prove either the root PID 1 socket activator before service startup or
a root peer PID in the exact
<code>/system.slice/agent-browser-lease-authority.service</code> cgroup after
startup. Both endpoint states bind the same protected socket inode before any
capability is sent. The active service independently validates its banked
executable before reading the request; ordinary clients do not need access to
the root process's <code>/proc/&lt;pid&gt;/exe</code> link.

## Operator request model

agent-browser owns browsers, profiles, tabs, queues, and job dispatch by default. Operators, agents, and software clients should usually request intent instead of taking direct responsibility for browser coordination. A normal request says which site, account, URL, or login identity is needed, what tab or browser action should happen, and which service, agent, and task owns the work. agent-browser then selects or reuses the right managed profile, attaches to an existing managed browser when possible, queues CDP control deterministically, and records the state needed for debugging. Profile records and profile allocation rows include `targetReadiness`, a no-launch readiness view for target services. Profile collections include `profileSources`, and profile lookup plus access-plan responses include `selectedProfileSource`, so operators can see whether the selected effective profile came from config, runtime observation, or persisted state. Built-in Google and Gmail targets without authenticated evidence use headed stealth Chromium and report attachable unknown readiness. Only a target whose effective policy requires CDP-free operation reports `needs_manual_seeding` and recommends detached `runtime login`. Once a managed profile lists the target in `authenticatedServiceIds`, readiness changes to `seeded_unknown_freshness` and access-plan no longer treats first-login seeding as a required manual action. HTTP clients and MCP agents can ask for the narrower profile selector through `GET /api/service/profiles/lookup` or MCP `agent-browser://profiles/lookup{?query,hostname,profileId,profileName,serviceName,targetServiceId,targetServiceIds,siteId,siteIds,loginId,loginIds,accountId,accountIds,authenticationState,freshnessState,tag,url,readinessProfileId,browserBuild}`. They can read one profile's readiness rows from `GET /api/service/profiles/<id>/readiness` or MCP `agent-browser://profiles/{profile_id}/readiness`, get the exact operator command and persisted lifecycle record from `GET /api/service/profiles/<id>/seeding-handoff` or MCP `agent-browser://profiles/{profile_id}/seeding-handoff{?targetServiceId,siteId,loginId}`, and update that lifecycle through `POST /api/service/profiles/<id>/seeding-handoff`.

Use `serviceName`, `agentName`, `taskName`, and target-service hints such as `targetServiceId`, `targetService`, `targetServiceIds`, or `targetServices` to make this request explicit. Callers that think in site, account, URL, or login vocabulary can use `siteId`, `siteIds`, `loginId`, `loginIds`, `accountId`, `accountIds`, or `url`; agent-browser normalizes those aliases into the same profile-selection request and derives known site-policy targets from URL origins. A service named `JournalDownloader` can request an ACS-authenticated tab for `probeACSwebsite`; agent-browser should decide whether the current ACS-authenticated profile and browser can be shared, whether a service-specific profile is required, or whether a new browser process is justified by isolation policy.

Operators can still request a particular managed runtime profile when they know the desired login state lives there. They can also bring their own profile with `--profile <path>` or equivalent API fields when they want more direct control over a browser identity. A custom path keeps its opaque service profile identity without becoming a named runtime profile. That is an override mode, not the default service model. The normal path is to let agent-browser perform deterministic profile selection, queue sharing, browser reuse, and collision avoidance so callers can spend their limited reasoning budget on the target workflow.

Software clients should not create a runtime profile just because another task
is active or because a site has a login. First call
<code>getServiceAccessPlan()</code> for the target identity, then request the
tab with <code>requestServiceTab</code> or <code>POST /api/service/request</code>.
When a client may need a recurring managed fallback profile, call
<code>acquireServiceLoginProfile()</code> instead so the registration and
readiness-monitor steps only happen after the broker reports no selected
profile.
Use <code>getServiceProfiles()</code> or
<code>getServiceProfileReadiness(&#123; id &#125;)</code> for narrower inspection
when a caller already knows which profile it is evaluating. Register a new
managed login profile only when agent-browser has no suitable profile, readiness
reports <code>needs_manual_seeding</code>, the operator wants a separate account
lane, or the client is explicitly bringing its own profile.

## Login Identity API Recipe

Software clients should request the identity they need, not the browser process they hope is free. Register the profile once with the target identities it can serve:

```ts
await registerServiceLoginProfile({
  baseUrl: `http://127.0.0.1:${streamPort}`,
  id: 'journal-acs',
  serviceName: 'JournalDownloader',
  loginId: 'acs',
});
```

Then request a tab by login identity through the service client:

```ts
await requestServiceTab({
  baseUrl: `http://127.0.0.1:${streamPort}`,
  serviceName: 'JournalDownloader',
  agentName: 'article-probe-agent',
  taskName: 'probeACSwebsite',
  loginId: 'acs',
  url: 'https://example.com',
});
```

For an existing managed session, agent-browser first inherits the profile proven by the exact current runtime owner. A request route hint cannot override the daemon's exact current route. A conflicting explicit profile fails, while retained session or browser observations without current ownership proof remain preserve-only. Only a genuinely new, unbound session can continue to the generic default. For new sessions, agent-browser first prefers profiles whose <code>authenticatedServiceIds</code> match the requested identity, then profiles whose <code>accountIds</code> match, then profiles whose <code>targetServiceIds</code> match, then profiles shared with the calling service through <code>sharedServiceIds</code>. Session records expose <code>profileSelectionReason</code> as <code>existing_owner</code>, <code>authenticated_target</code>, <code>account_match</code>, <code>target_match</code>, <code>service_allow_list</code>, <code>browser_build_default</code>, or <code>explicit_profile</code>, and launch events mirror that value in <code>details.profileSelectionReason</code>. They also expose <code>profileLeaseDisposition</code> as <code>new_browser</code>, <code>reused_browser</code>, or <code>active_lease_conflict</code> plus <code>profileLeaseConflictSessionIds</code> when another exclusive session already references the same profile. Service-scoped launches reject active exclusive profile conflicts by default before browser start; set <code>profileLeasePolicy: "wait"</code> and <code>profileLeaseWaitTimeoutMs</code> to wait for release instead. Access-plan <code>decision.profileReuse</code> makes the sharing model explicit: authenticated profiles use <code>profileProcessPolicy: "exclusive_process"</code>, while compatible clients share the retained browser through <code>clientSharingPolicy: "shared_browser_tabs"</code> and <code>defaultAcquisition: "tab_new"</code> when reuse is available. <code>decision.profileReuse.sharedAcquisition</code> names the structured acquisition mode, route hint fields, retained browser/session hints, queue serialization, cleanup expectation, and duplicate-process policy so clients do not infer sharing behavior from raw profile state. Same-session retained browser reuse remains allowed. Use explicit <code>profile</code> or <code>runtimeProfile</code> request fields only for override workflows where the caller intentionally takes responsibility for the browser identity.

For example, CanvaCLI should request <code>serviceName: "CanvaCLI"</code> plus
<code>loginId: "canva"</code> or <code>targetServiceId: "canva"</code>. If no
suitable managed Canva profile exists, register one with
<code>registerServiceLoginProfile(&#123; id: "canva-default", serviceName: "CanvaCLI", loginId: "canva", authenticated: false &#125;)</code>,
seed it when readiness says manual seeding is needed, and keep future work
identity-based instead of profile-name-based.

HTTP <code>GET /api/service/profiles/&lt;id&gt;/allocation</code> and MCP `agent-browser://profiles/{profile_id}/allocation` return one derived profile allocation row when a caller wants current holder, waiting job, conflict, lease state, browser ownership, compact browser health, and recommended-action data without fetching the full profile collection.

Software clients can call <code>summarizeServiceProfileAllocationBrowserHealth()</code> on <code>getServiceProfileAllocation()</code> or any <code>profileAllocations</code> row to produce the same compact browser-health labels shown by <code>agent-browser service profiles</code>. If the client already has an access-plan response, <code>getServiceProfileAllocationForAccessPlan()</code> fetches the broker-selected profile allocation without manually unpacking <code>selectedProfile.id</code>. The summary helper returns <code>compact</code>, <code>compactLabels</code>, ready and non-ready browser IDs, health states, and an inspection recommendation for logs, traces, and operator-facing status output.

Waiting lease requests stay queued until the selected profile becomes available or <code>profileLeaseWaitTimeoutMs</code> expires.

## Profile and session planning

Runtime profiles are the safest default for recurring automation because they keep Chrome user data, cookies, site storage, and login state in a managed path. A single profile can represent one user identity per site, so profile allocation is a service design decision:

- Use one shared profile when several tasks intentionally operate as the same browser identity.
- Use a service-specific profile when a service needs durable login state but should not share cookies or extensions with unrelated services.
- Prefer the profile that has credentials and usable auth state for the target site or identity provider.
- Use a separate browser process when profile isolation, keyring behavior, extension state, or resource ownership matters more than process count.
- Use a custom `--profile <path>` only when an external profile directory is part of the contract.

New Google and Gmail profiles use headed <code>stealthcdp_chromium</code> and may keep CDP attached during first sign-in. Register the profile as unauthenticated, let automation attempt the sign-in flow, and request operator intervention only after a failed attempt, challenge, passkey prompt, or plugin setup that automation cannot complete. When an effective site policy sets <code>requiresCdpFree</code>, use the detached headed flow instead: omit <code>--attachable</code> and any DevTools port, complete the required setup, close Chrome, then relaunch through service-owned automation. Structured <code>targetReadiness</code> rows expose the applicable posture through <code>seedingMode</code> and <code>cdpAttachmentAllowedDuringSeeding</code>.

When readiness actually requires manual seeding, use <code>agent-browser service profiles &lt;profile-id&gt; seeding-handoff &lt;target-service-id&gt;</code>, <code>GET /api/service/profiles/&lt;profile-id&gt;/seeding-handoff?targetServiceId=&lt;target-service-id&gt;</code>, or MCP `agent-browser://profiles/{profile_id}/seeding-handoff{?targetServiceId,siteId,loginId}` to turn the readiness row into the exact detached runtime-login command, setup URL, operator steps, warnings, persisted lifecycle record, and <code>operatorIntervention</code> payload. agent-browser owns that intervention contract: <code>state</code>, <code>severity</code>, default channels, optional desktop/webhook, and agent notification channels, completion signals, lease blocking, and safe or dangerous actions. Dashboards, agents, desktop popups, and software clients should render that payload instead of inventing independent seeding rules. Use <code>POST /api/service/profiles/&lt;profile-id&gt;/seeding-handoff</code> or <code>updateServiceProfileSeedingHandoff()</code> to move the lifecycle through detached launch, waiting for close, declared complete, closed but unverified, verified fresh, failed, or abandoned states. Non-attachable <code>runtime login</code> records the seeding browser PID when the runtime profile maps to a known manual-seeding target, and later runtime or service reads mark the handoff closed but unverified once that PID exits. After the bounded post-close auth probe, run <code>agent-browser service profiles &lt;profile-id&gt; verify-seeding &lt;target-service-id&gt; --state fresh --evidence &lt;probe-evidence&gt;</code>, call <code>verifyServiceProfileSeeding()</code>, or adapt <code>examples/service-client/post-seeding-probe.mjs</code>; all three paths reuse profile freshness and move the matching handoff to <code>verification_pending</code> for inconclusive or non-fresh evidence, or to <code>fresh</code> when the probe reports usable authenticated state. Add <code>--account-id &lt;id&gt;</code> or <code>--account-ids &lt;id,id&gt;</code> to the CLI write when the same verified browser profile should be selectable by account label as well as by authenticated target. Desktop popups are optional and policy controlled; they are notification providers, not the primary control plane.

Configured service profiles and sessions can describe ownership, lease behavior, cleanup policy, keyring posture, browser linkage, caller labels, intended target services, intended account identities, currently believed authenticated target services, the reason a profile was selected, and whether the selected profile opened a new browser, reused a retained browser, or overlapped another exclusive session. `targetServiceIds` records target sites or identity providers such as `google`, `microsoft`, or `acs`; `accountIds` records user, tenant, or account identities; `authenticatedServiceIds` records targets currently believed to have usable login state. Profile writes reject `caller_supplied` records without `userDataDir` and `per_service` records with multiple `sharedServiceIds` values. Session writes infer `owner` from `agentName`, then `serviceName`, when omitted; `profileId` must reference a persisted profile, and profile `sharedServiceIds` allow-lists are enforced. Explicit `--runtime-profile` and `--profile` values still win. When a launch command omits both, `serviceName` plus `targetServiceId`, `targetService`, `targetServiceIds`, `targetServices`, `siteId`, `siteIds`, `loginId`, `loginIds`, `accountId`, `accountIds`, or `url` lets agent-browser choose a persisted service profile. The selector first prefers `authenticatedServiceIds` matches, then `accountIds` matches, then `targetServiceIds` matches, then the caller `sharedServiceIds` match. MCP typed browser tools and `service_request` accept the same target profile hints, so clients can stay on typed schemas or send one explicit service request object for profile-aware first commands. Run `pnpm test:service-profile-target-mcp-live` to validate this live MCP path.

Software clients that register recurring managed login profiles should also add a retained freshness monitor for the same target identity. Use <code>upsertServiceProfileReadinessMonitor()</code> from <code>@agent-browser/client/service-observability</code> or write a monitor with target <code>&#123; "profile_readiness": "acs" &#125;</code> through <code>POST /api/service/monitors/&lt;id&gt;</code>. The monitor is no-launch: it checks retained <code>targetReadiness</code>, marks expired fresh rows stale, removes the expired target from <code>authenticatedServiceIds</code>, and lets access-plan <code>monitorFindings</code> warn callers before they request a tab. Access-plan also flags matching monitors that are due or never checked so clients can run <code>service_monitors_run_due</code>, <code>runDueServiceMonitors()</code>, or <code>runServiceAccessPlanMonitorRunDue()</code> before relying on retained auth state. The run-due response returns per-monitor <code>results</code>, so clients can confirm the relevant <code>profile_readiness</code> target produced <code>profile_readiness_fresh</code>, <code>profile_readiness_expired</code>, <code>profile_readiness_not_fresh</code>, or <code>profile_readiness_missing</code> and inspect any affected <code>staleProfileIds</code>.

The generic <code>examples/service-client/service-request-trace.mjs</code> workflow demonstrates this path for non-Canva clients. Pass <code>--register-profile-id</code> with <code>--register-readiness-monitor</code> when a recurring service-owned profile may be needed. The example calls <code>acquireServiceLoginProfile()</code> so the client asks for the access plan first, registers the fallback profile only when no profile is selected, adds the freshness monitor for that fallback profile, refreshes the access plan, submits the planned tab request through the service queue, and prints copyable trace plus incident handoff references for follow-up agents or software clients.

Pass <code>--run-due-readiness-monitor</code> to the same example when the client should execute an access-plan-recommended freshness monitor before using the retained profile. Pass <code>--run-browser-capability-preflight</code> when the client should execute the final access plan's no-launch browser-capability gate before requesting browser work.

## Browser health and recovery

Service reconciliation probes persisted browser records and updates health before clients make decisions from stale state. It also compares retained RDP route-pool entries with their live X11 sockets, expires due or orphaned service session leases without launching a browser, and reports <code>expiredSessionLeases</code>, <code>expiredSessionLeaseCount</code>, and <code>remoteViewRepair</code> in reconcile responses. Missing route displays invalidate their pool entries and orphan linked checked-out routes. Restored sockets return those entries to available, and orphaned route owners release stale checkouts while leaving independently running browser windows untouched. Local process exits are marked `process_exited`. CDP endpoints with a live process but failed CDP connection are marked `cdp_disconnected`. Endpoints without a live process are marked `unreachable`. Endpoints that answer health probes but fail target discovery are marked `degraded`.

When a queued browser command finds that the active browser has exited or CDP is disconnected, agent-browser records the failure before cleanup and relaunch. Recovery traces show the health transition, recovery start, retry budget, policy source, next retry delay, and the final ready transition when relaunch succeeds.

Close handling uses two remedies. First, agent-browser attempts a polite browser shutdown. If polite shutdown fails, the browser record is degraded. Then it force kills owned browser processes when needed. If force kill fails, the browser record is faulted and the incident can escalate as possible OS degradation.

Run `pnpm test:service-shutdown-faulted-live` to validate the faulted shutdown path.

## Service records

Reconciliation removes a legacy degraded, profile-less late-close browser row only when its exact owner generation proves terminal process exit and profile-lock release, cleanup is satisfied, and no operational session, tab, process identity, or presentation remains. It preserves the close failure in a `terminal_degraded_placeholder_removed` reconciliation event and retains the lifecycle evidence. Missing or conflicting proof keeps the row for inspection.

The CLI, HTTP API, MCP resources, and dashboard share the same service concepts:

- `profiles` describe durable browser identity and launch policy.
- `sessions` describe service or agent ownership of browser work.
- `browsers` describe process, CDP, health, and recovery state.
- `tabs` describe live page and webview targets discovered from CDP.
- `jobs` describe queued, waiting-on-profile-lease, running, succeeded, failed, cancelled, and timed-out service work.
- `controlPlane.waitingProfileLeaseJobCount` summarizes current profile lease wait pressure without requiring a separate jobs query.
- `incidents` group operational issues with severity, escalation, handling state, and recommended action.
- `events` record launch, reconciliation, health, recovery, profile lease wait, tab lifecycle, and incident-handling changes.
- `sitePolicies`, `providers`, and `challenges` describe site-specific automation posture, browser providers, and retained challenge state.

The repo keeps JSON schemas for these contracts under `docs/dev/contracts/`. HTTP and MCP collection envelopes are expected to remain aligned with those schemas.

## MCP shape

Run `agent-browser mcp serve` for the workflow catalog. `tools/list` advertises
12 tools: open, five common page actions, task-scoped tabs, handoff, continuation,
close, advanced browser commands and explicit discovery. All page actions use the
`taskId` returned by `browser_open`; agents do not acquire leases or select routes.

```json
{"name":"browser_open","arguments":{"profile":"editorial","profileMode":"persistent","taskKey":"edit","url":"https://example.com"}}
```

Call `browser_snapshot` and common page actions with that task ID. For another
page operation, request its schema first:

```json
{"name":"browser_discover","arguments":{"category":"browser","operation":"press"}}
```

Then execute the page arguments in `params`:

```json
{"name":"browser_command","arguments":{"taskId":"<returned-task-id>","action":"press","params":{"key":"Enter"}}}
```

Use `browser_tab` with `operation` set to `list`, `new`, `select` or `close`.
Creation requires a stable `tabKey`; repeating it returns the retained tab.
Selection and closure accept only this task's tabs. `browser_close` ends this
task while preserving peer work and persistent profile data.

Use `browser_handoff` to obtain a ready, complete native Remote View URL. The
person opens that URL using the native viewer's existing authentication. After
human input, `browser_continue` retains the task and current page.

`browser_discover` also supplies diagnostic and administrative CLI/API metadata
on demand. It does not execute maintenance. Old service tools, raw tab tools and
retired lease/recovery/repair/reset MCP operations are unavailable. The advanced
browser command cannot dispatch service authority actions or override task,
profile, tab or route selectors. There is no legacy catalog mode.

The compact operating guide is available at `agent-browser://operating-guide`.
Read-only service resources remain explicit diagnostic reads; they are not
prerequisites for opening or continuing a browser task.

## Dashboard operations

The dashboard service view is the operator surface for long-lived automation. It should organize multiple services and agents at the same time, show named tasks, expose service traces and incidents, and make browser state inspectable without requiring every operator to attach directly to Chrome. The top scan path uses compact status lights for worker health, browser health, reconciliation, events, jobs, and retained service records. Retained-record totals are hover details unless reconciliation fails or retained state grows large enough to need cleanup. The managed browser table defaults to actionable records, so live, degraded, faulted, process-exited, and otherwise inspectable browser records stay visible while inert retained <code>not_started</code> placeholders remain available behind retained or all-record filters. Operators can switch between compact, standard, and expanded row density, hide secondary browser table columns, and resize visible columns while preserving row inspection. The toolbar groups record lifecycle, density, and layout controls separately so the scan path stays compact. The dashboard remembers those lifecycle, density, visibility, and width choices locally, and the table menu includes a full table-view reset that clears those saved preferences together. Secondary workspace tabs distinguish active work from retained history: Sessions reports active sessions and ready or loading tabs separately from retained rows, and Jobs reports queued or running work separately from terminal retained jobs. Profile allocation rows name the retained owner browser, shared service/agent/task clients, lease conflicts, tabs, and duplicate-launch guidance so shared runtime profiles can be inspected without parsing raw JSON. The Jobs workspace can filter by text, state, and requested display allocation, then sort retained jobs by time, state, action, display allocation, service, or task. Trace display-allocation summary cards switch directly to the Jobs workspace with the matching display filter, so operators can inspect the jobs behind private, shared, ambient, or unrecorded display requests without reconstructing the filter manually. On desktop, Service rows use a list-detail layout: selecting a browser, profile allocation, incident, session, tab, or job row opens its operational details in the collapsible right pane. Selected incident rows expose acknowledge and resolve actions in that pane, selected incidents can jump back to the related trace, and selected queued or running jobs expose cancel there. The trace explorer includes copyable CLI and HTTP handoff strings, ownership summary rows, browser capability launch decisions, profile lease wait cards plus normalized timeline job rows that jump to their retained Jobs row, incident-backed timeline rows that jump to their retained Incidents row, and the normalized timeline so operators can see why a service received a particular browser build or executable.

When live browser viewing is enabled, use it as an inspection and intervention surface, not as the source of truth. Service records, trace entries, and job or incident state remain the durable control-plane state. Browser details and service tab rows can open embeddable view streams, including RDP gateway streams, in a dashboard dialog with a fullscreen toggle. Embedded Guacamole viewports detect the gateway's single-active-viewer disconnect state and show a Take over action so another dashboard or popout can be served deliberately. The normal remote-headed view target is the selected browser's private display. Shared displays are allowed only when configured explicitly and should still be mediated by queued focus requests. Guacamole route-pool entries can include a route descriptor with <code>localEmbedUrl</code>, <code>publicOperatorUrl</code>, <code>healthUrl</code>, and <code>dashboardEmbedUrl</code>. Local dashboard iframes should prefer the local embed URL. The durable <code>/remote-view/&lt;handoff-id&gt;</code> route may resolve through the public provider ingress, but agents must not give that provider URL directly to the operator. Tab inspection requests a queued <code>view_focus</code> service action with the selected tab's <code>targetId</code> plus a stable <code>index</code> when both are known, or the index alone when no target ID is present; that action retries the index when retained target state is stale, switches to the tab, calls <code>Page.bringToFront</code>, and asks Chrome to maximize the containing native window before the iframe opens.

### Retained browser temporary storage

The Linux runtime host mounts private, mode-0700 state directories at `/tmp` and
`/var/tmp`. Their backing storage survives host retirement so retained browsers
can still create temporary files. It is scoped by the systemd unit name under
the user state directory. Never remove that storage while a retained browser
references it. Replacing the unit does not repair a browser already holding a
deleted temporary directory; that requires a separate ownership-preserving
recovery.

### Production presentation recovery inventory

Production recovery inventory uses `AGENT_BROWSER_PRODUCTION_PRESENTATION_INVENTORY_PATH`
(an absolute path) and schema `agent-browser.production-presentation-inventory.v1`.
The CLI dotenv loader applies this path and the presentation capacity settings
to direct and staged runtime-host launches from `~/.agent-browser/.env`.
Set `environment` to `production`, `bootEpoch` to the current boot identity, and
provide `routes` containing `routePoolEntryId`, `routeId`, `displayAllocationId`,
`displayName`, `routeUser`, and `connectionId`. Every entry must match existing
Service custody and current process/display ownership. This configures capacity
without rewriting route records or claiming operator visibility. Existing human
controllers and capacity reservations remain protected. Do not also configure
`AGENT_BROWSER_PRESENTATION_PROVIDER_INVENTORY_PATH`, which remains development-only.
Set the existing `AGENT_BROWSER_PRESENTATION_WARM_MINIMUM`,
`AGENT_BROWSER_PRESENTATION_HARD_MAXIMUM`, `AGENT_BROWSER_PRESENTATION_HUMAN_RESERVE`,
`AGENT_BROWSER_PRESENTATION_RECOVERY_RESERVE`, and
`AGENT_BROWSER_PRESENTATION_MAX_QUEUE_DEPTH` for the admitted provider inventory.
A changed boot or binding requires requalification; never relabel a development
inventory as production.
If production inventory validation fails, Service State remains readable and
retains existing custody. `presentationCapacity.admissionError` and the capacity
projection’s `bindingWarnings` report the cause; admitted capacity becomes zero
and new presentation effects are refused with `inventory_admission`. Restore
the configured inventory and its ownership evidence to requalify capacity.
Ordinary browser diagnostics remain available during the outage.

## Inspect browser mode

Each managed browser has an SVG mode button in the rail. Hover, click or use
keyboard activation to inspect CDP, No CDP or Unverified evidence without
selecting a tab or changing the browser. Refresh inventory requests another
read-only observation. Old or missing evidence remains Unverified.

Agents discover category `browser`, operation `mode`, then use `browser_command`
with the existing `taskId` and action `mode`. CLI clients use
`agent-browser --json mcp browser-mode <task-id>`. HTTP clients read the
`browserRuntime.workspace.browsers` map from
`GET /api/service/status?projection=workspace`; ordinary Service status includes
this evidence too. All routes use the owner's original-process identity.

The reported executable name and family omit private directories and launch
arguments. Browser version remains unknown until separately observed. Debugging
posture does not prove native input, viewer readiness or authentication. This
inspection does not relaunch the browser or attach a debugger. Mode conversion
and agentic CDP-free desktop input are separate delivery work.


Native task observation and input use the existing Remote View owner. MCP
`browser_command` supports `native_capture` and `native_input`; discover their
arguments with `browser_discover`. CLI equivalent:
`agent-browser --json mcp browser-native TASK native_input '{"actions":[{"kind":"key","chord":"Tab"}]}'`.
HTTP clients send the same action, exact `sessionId` and `sessionName` to
`POST /api/command`. Capture returns a fresh, process-fenced window region;
input reports delivery separately from completed page effects. Observe after
an uncertain reply before deciding another input is appropriate. These actions
never attach CDP, acquire another task, or return explicit human takeover.
An unavailable Native owner or changed process/window returns remediation.
For an existing scoped `browser_policy` override, send `policyOverrideId` and
`requestId` at the top level of `browser_command` for either Native action.
The grant must match the exact task, action, request and current policy; a
mismatch remains denied. Preserving request identity never authorizes replay of
uncertain input. CLI `mcp browser-native` JSON uses the same `policyOverrideId`
and `requestId`. Raw HTTP `POST /api/command` sends `policyOverrideId` and
the matching request identity as `id`, together with exact `sessionId` and
`sessionName`; it does not use a `requestId` alias.
Mode conversion remains a separate explicit owner operation.

Select `pause_and_relaunch` to hold the operation in `paused` before closing
anything. Affected tasks stay fenced against page and Native automation. Later
select `relaunch`, confirming when the returned action requires it, or cancel
the pause. There is no automatic timed restart. Immediate relaunch is separate.
To cancel conversion at a close prompt, the owner sends Escape and rechecks the
exact live original process and Native window before releasing the operation.
A lost input reply or failed readback keeps custody. Inspect the original page
before continuing; input delivery alone does not prove a page or dialog result.


Inspect the original operation after a failed launch. Copy readback separates
`copyComplete` and `profilePublished` from `launchStatus` and `destinationTask`.
For `launch_absent`, explicitly confirm `retry_launch` or
`finish_without_opening`; the latter retains the published independent copy.
Mode `launch_absent` offers confirmed `relaunch` or `restore_previous`.
A launched replacement with unavailable Native readiness reports
`replacement_pending`; confirmed `restore_previous` selects the original mode
through the same operation. Unknown launches and copy `launch_pending` first
`reconcile` the original operation and exact task. Never repeat the copy or
blindly launch again. Restoration preserves requested-mode history, reports
its effective mode, and does not replay uncertain website submissions.

An already published replacement is a completed physical outcome even when the
final operation-journal write was lost. A restore request then seals the original
operation and reports `mode_operation_already_completed`, preserving the current
browser. Start a new explicit conversion to select another configuration.

To find retained work after reload, send `choice: "inspect"` through the same
`mode_convert` or `profile_duplicate` route. Omit `operationId` to list matching
operations, or include it for one retained operation. Mode lookup requires the
exact task; profile-copy lookup binds the source profile and optional exact
task. The read-only `agent-browser.browser-operations.v1` response includes safe
operation IDs, kinds, task/profile/browser bindings and supported actions. It
never closes, launches or copies a browser. Select the original operation before
continuing; multiple matching copies require an explicit selection. A busy
response identifies the active operation instead of admitting a replacement ID.
The rail reads this owner state when reopened, without persisting profile paths
or credentials in client storage. CLI JSON requests use `choice: "inspect"`
with `mcp mode-convert` or `mcp profile-duplicate`; HTTP uses the same existing
owner actions at `POST /api/command`.

Inspection returns at most 256 matching operations after task/browser filtering,
with the exact active operation and pending work first. `historyTruncated`
reports omitted retained history. Supply a known `operationId` for exact older
readback; inspection and selection still have no browser effects.




The rail's browser-mode menu offers **Duplicate profile**. Enter a copy name,
review affected tasks, and select the returned action. A running source closes
only after the selected confirmation. A source without qualified clean-close
history offers **Open source for review**. The copy has a new identity and
writable directory; source and copy evolve independently. Copy success does
not prove that stored authentication works in the copy.

MCP: discover `profile_duplicate`, then use `browser_command` with
`action: "profile_duplicate"` and `params` containing `operationId`,
`sourceProfileId`, `destinationName`, `choice` and `launch`. An optional `taskId`
binds the source profile to that task. CLI:
`agent-browser --json mcp profile-duplicate '{"operationId":"copy-one","sourceProfileId":"PROFILE","destinationName":"Independent copy","choice":"prepare","launch":true}'`.
HTTP: send these fields and `action: "browser_session_profile_duplicate"` to
`POST /api/command`. Follow the returned actions using the same `operationId`;
set `ownerConfirmed: true` only for the explicitly selected consequential
choice. After a lost reply, reconcile that operation before attempting another
effect. Cancelling a request does not reopen a source already stopped.
