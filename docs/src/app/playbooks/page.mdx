# SiteGuides and website routines

Agents and software can run a shared routine against an existing browser task.
A SiteGuide describes website states and receiving identity checks. A playbook
composes routines while preserving that task.

## Verify an existing login

Discover the focused metadata with `browser_discover` category `playbooks`.
Request the `verify_login` operation for its schema, then use `browser_command`:

```json
{"taskId":"<existing task>","action":"playbook","params":{"operation":"verify_login","guideId":"bill-session-v1","accountRef":"<expected account>","organizationRef":"<expected company>"}}
```

Verification reads bounded state/identity predicates, performs no credential
submission and preserves peer tasks. A stale observation or changed task target
cannot produce completion. The default observation window is 10000 ms;
`maxObservationAgeMs` accepts 1 through 60000.

## Use from software

```js
import {createPlaybookClient} from '@agent-browser/client/playbooks';
const routines = createPlaybookClient((name, args) =>
  client.callTool({name, arguments: args}));
const result = await routines.verifyLogin({taskId, guideId, accountRef, organizationRef});
```

`listGuides(taskId)` and `inspectGuide(taskId, guideId)` read the configured
registry. The existing MCP client provides transport; the routines create no
second task or credential store.

## Configure site knowledge

Set `AGENT_BROWSER_SITEGUIDE_DIRECTORY` on the MCP server to a directory of
reviewed `agent-browser.siteguide.v1` JSON files named by guideId. Each file is
bounded to 64 KiB. A guide declares exact origins, an authenticated application
selector, expected-identity locators and state selectors. It carries no account
selection, credentials or private runtime state.

The bundled BILL guide is a starter template. Validate its controls from current
observations and synthetic fixtures before relying on it for a real account.
Remote View supplies desktop interaction; shared auth helpers supply private
credential/MFA operations. Session verification alone does not prove either
provider integration or completed login automation.

## Standalone Auth client

`connectHostedAuthHelper()` now defaults to the independently installed Auth
Receipts SDK. Owner setup selects `auth-receipts/client/current` under the data
directory; no Bots installation or per-task SDK override is needed. Auth's candidate
builder supplies the hash-bound verification manifest. The trusted SDK owns
private `AUTH_RECEIPTS_DISCOVERY_FILE` discovery and connection rotation. Missing,
unsafe or incompatible SDKs fail explicitly rather than using legacy credentials.
Installed/source/provider qualification remains separate.

## Owner-authority login and factors

Import `createOwnerLoginPlaybook`, `createOwnerTotpContinuation` and
`createOwnerNumberMatchingContinuation` from the existing login-playbook entry.
All use the connected standalone `auth` client, trusted `browser` routines and
metadata `checkpoints`. Owner login resolves service/account intent into the
existing owner review and private-use lifecycle. Exact task/profile/browser/tab/
generation and current account/company evidence are required. Typed holds preserve
missing prerequisites; a profile name is not identity proof.

TOTP uses Auth's observed continuation, including after SSO. After password use,
retain `originalRequestId` so Auth can bind an account-less factor screen to the
original attempt. The helper creates the factor request through that observed
continuation, preserving Auth's account and receiving checks. Number matching uses
an existing private attempt and Auth's owner-only reverse-input path. Capabilities
are receiving-path-specific: a browser-client TOTP route does not establish native
number-matching or accessibility qualification. Neither factory returns codes or
creates policy. Unknown input is retained without a new credential request.
Owner login `reconcile: true` only reads an existing checkpoint/request.

Before private use is attempted, owner login may renew a typed `plan_stale` hold caused by owner-review delay. Renewal requires complete, unchanged guide, control, expected-state and task/profile/browser/tab bindings with the same receiving generation. The fresh plan is validated and durably saved against the original request before dispatch intent. Missing or changed proof stays held; attempted or unknown input never renews a plan or creates replacement approval.

Optional `browserActionEvidence` v1 describes protected input and submission
acknowledgement for the exact request/attempt/generation. Dispatch is not server
acceptance or authenticated identity, and this evidence never grants retry rights.

## Retained legacy callback checkpoints

`@agent-browser/client/login-playbook` exports `createLoginPlaybook` with an
existing routine client, a trusted auth-helper callback and a durable metadata
checkpoint store. Use `connectHostedAuthHelper()` from
`@agent-browser/client/hosted-auth-helper` for verified installed SDK discovery.
Pass its `helper` and attested `callerTaskId` to the login playbook. Discovery
keeps bearer material inside the private producer transport. Configured
`list_accounts` metadata and the existing source owner select account/source;
a browser profile name is not a credential reference.

An ordinary Codex caller needs no Bots roster entry or TUI. Its callerTaskId
identifies its work, while taskId addresses the browser. Version2 independently
freezes the exact receiving provider/task/profile/browser/tab. The hosted path
uses request_login, inspect_request and begin_authentication; legacy callbacks
retain authenticate. Credentials and factors stay inside trusted host receiving
ports. These operations describe retained legacy checkpoints. New credential requests
use the standalone owner factory above; Bots is not Auth authority.

Each advance returns the next actionable state. Preserve the original scope,
task and expiry when continuing. The adapter records intent before submission
and inspects the original request after a timeout or restart. It never blindly
resubmits an uncertain login. Completion requires helper captureState ready
plus current SiteGuide evidence for the intended account and company.

After independent human/browser completion, call
`login.advance({...originalOptions, reconcile: true})` with the original durable
checkpoint. It reads back the same request and cannot create a replacement,
retrieve credentials, start private authentication or replay unknown input.
Running work is inspected. Missing checkpoints fail; unsupported readback returns
helper_reconciliation_unavailable. Expiry/revocation are never renewed.

The trusted receiver independently verifies the current principal and supplies
reconciliation-specific native safety evidence. A saved email on a login chooser
is not authentication. Missing safety stays held even if the principal matches;
negative readback sends no input. Company verification remains an independent
SiteGuide step after helper capture is ready.

A failed login-only request may retire with helper_attempt_released only when
its trusted owner proves from durable before-effect records that no protected
input was attempted, or independently proves every current protected field empty,
and independently verifies a current clean login/native capture. Current safety
does not erase a recorded password/factor attempt. Readback cannot clear fields
or fetch another credential/factor. Timeout or page state alone is insufficient.
The old request, target, expiry and input history remain; earlier effects stay unknown.
The playbook reports failed and cannot replay that grant. Preserve its checkpoint;
a subsequent operation is separately selected under the task's authority.

Shared host receiving ports sequence observed identifier/password and configured
private MFA states. Remote View supplies process/window/visual-fenced native
input with private empty-field/value checks. A trusted observation may identify
a dismissible popup for one guarded Escape before a fresh hit-tested submit;
unknown dismissal or submit acknowledgments never authorize replay. An exact
current identifier match is preserved without clearing or retyping after fresh
control and native-owner checks. Unknown prior delivery cannot become equality
success. Password and factor replacement checks remain unchanged.

The installed independent native dummy qualifies hosted discovery, private input,
observer/native safety, held-request restart and independent readback. Real
account/company acceptance, password-manager/passkeys and automated MFA remain
separate qualifications. Cooperative privacy does not suppress unintegrated
Remote View capture or existing viewer streams. Task tab listing attributes live
popup opener chains; after capture is ready, the playbook continues in the sole
verified owned destination while preserving peers. Unattributable extension tabs
still need an owner binding rather than a guessed URL. The default Agent Browser
MCP catalog is unchanged.

## QBO and receiving controls

The qbo-session-v1 starter uses the same task, routine, helper and checkpoint
interfaces as BILL. Its company identity is a realm reference. An authenticated
QBO browser is separate from QBO OAuth/API readiness and accounting operations.

A reviewed guide may include controls with identifier, password, submit and
accountScope selectors, plus identifierSubmit for a separate identifier step.
The trusted receiving adapter consumes this metadata before private input;
credential values and MFA material never appear in a guide. The owned QBO
fixture qualifies identifier-first and password-first variants, human MFA waiting,
asynchronous popup continuation and exact realm verification. Starter controls
require current site evidence before real-account use.

## Prepare actions and propose guide versions

Discover prepare_login and validate_plan in the same focused playbooks category.
The client methods `prepareLogin(options)` and `validatePlan({...options, plan})`
use the existing task. Preparation freezes reviewed guide identity, control
fingerprint, expected state and freshness. A plan_prepared result means that
preparation completed; receiving login has not been verified.

The private login adapter validates this plan before the helper retrieves a
credential. Changed controls produce adaptation_required with no input. A stale
observation of unchanged controls can refresh under the same request. Controller
changes preserve the checkpoint and helper request/action identity.
The login client requires prepareLogin and validatePlan. After reviewing changed controls, pass a freshly prepared plan as reviewedPlan to advance with the same options and retained guideId. It validates the replacement against the current task before saving it and retains the helper request/action. Reviewed guide content may change under that retained identifier through the candidate registry. A typed pre-input helper refusal can be retried only after exact-request inspection proves approved state with no started or input-attempt timestamp; a lost acknowledgement never permits retry.

Password preparation requires a masked input; an unmasked replacement cannot
become an authorized action merely by observing it afresh.

Develop a guide from owned synthetic observations and explicit receiving
assertions. When the site changes, place a proposed version outside the shared
registry and test it through a candidate client configured with that directory.
The authoring fixture demonstrates this with a changed password control and a
v2 proposal, preserving the original task and canonical guide. Publication uses
ordinary reviewed source changes; successful improvisation does not publish.

## Collect a bounded feed

collect_posts and the client collectPosts method use the same existing task and
result envelope. A retrieval guide declares container/item selectors, ID
attribute, title/link selectors, explicit no-results marker and optional next
page selector. Login/account fields are optional for this non-login workflow.

Defaults are 50 items, one page and zero scrolls; maximums are 200 items, 10 pages
and 10 scrolls. Fresh observation and link revalidation precede navigation.
Website DOM scrolling consumes a visible budget. Normalized item data contains
IDs, bounded titles and HTTP(S) origin/path links with query/fragment removed.

Explicit no-results, unproven empty extraction, malformed items, login/blocked
pages and partial output have distinct reasons. Coverage includes pagesUsed,
scrollsUsed and observations; partial records do not establish complete coverage.
The Reddit guide is a starter and the owned fixture is the qualified target.
Research/ranking policy stays downstream; no live social requests are included.
