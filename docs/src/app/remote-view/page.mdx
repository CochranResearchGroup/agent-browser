# Browser work with Remote View

Agent Browser should make browser work easier to complete, hand to a person,
and continue afterward. It owns browser automation and task-appropriate profiles;
Remote View owns desktop operation and the native human viewer.

The operator experience is a direct desktop link through Remote View's existing
authentication, including production Authelia. Human interaction and automation
continue in the same browser. Prefer a chooser showing Agent Browser-owned
desktops. A dashboard, duplicate viewer, extra Open desktop step or additional
Agent Browser viewer-grant ceremony is not part of the intended workflow.

Use an existing client profile, a managed persistent profile or a disposable
profile as the task requires. Preserve existing authentication where needed.
Validate responsive viewing and controls, continued automation and predictable
cleanup. This describes the governing direction; the repository RUNBOOK records
current implementation and acceptance gaps.

## Hosted reconnect, rules and artifacts

The connected MCP catalog has 16 workflow tools. Discover actual schemas before
use; the source guide does not prove installed support.

`browser_reconnect` accepts taskId and operation status, disconnect, reconnect,
rebind, configure or reopen. All changes require requestId and expectedRevision
from current status. configure requires lossPolicy report_only or reopen; rebind
requires desktop with desktopId/generation. Status is metadata-only; reconnect
freshly verifies the retained process and Native assignment without launch.
BrowserUnreachable, positively absent BrowserLost and RebindRequired are distinct.
recoveryDesktop is nullable approved recovery intent. Default loss policy reports loss. Explicit reopen requires opt-in and no pending
uncertain effects: managed browsers reopen empty/blank without replaying history;
borrowed browsers require the app's fresh attachment and desktop proof and never
launch an app browser. Human control remains held. Results include reconnect
revision/state/lossPolicy/lastRequestId/observedDesktop/pending/automaticReplay:false.


When the original managed process is positively absent, explicit rebind may retain
an exact current ready desktop as approved recoveryDesktop. State stays
browser_lost: this records a future recovery destination, not a physical move,
connection or rewrite of the old browser binding. A subsequent explicit reopen
under lossPolicy reopen requires agent ownership and no pending effects. Only a
verified replacement on that approved target publishes its new physical binding
and clears recoveryDesktop. Live managed generation-changing rebind remains
capability-refused. PID-reuse absence is conservatively blocked. Borrowed reopen
still requires fresh app attachment/desktop proof and preserves any human hold.
This source contract's new recovery path still needs native custody qualification.

```bash
agent-browser --json mcp host-reconnect TASK status
agent-browser --json mcp host-reconnect TASK configure '{"requestId":"loss-policy-1","expectedRevision":0,"lossPolicy":"report_only"}'
```

`browser_policy` takes taskId and operation status, set_app, set_task, clear_app,
clear_task or override. Mutations require expectedRevision, actor and reason.
Policy version 1 contains deniedActions and artifactDestinations mapping a handle
to an absolute canonical existing directory. A task policy completely replaces
app defaults; clear_task restores them. Optional browser_open taskPolicy
uses that same v1 shape to bind an explicit task override before launch. Unrestricted tasks require no extra grant.
Scoped overrideAction/requestId returns overrideId for policyOverrideId on that
exact task/action/request/current policy, never to bypass human control or peers.
Pass policyOverrideId and requestId at the top level of the supported page tool
or browser_command; for example action fill with params selector/value.

`browser_artifact` takes taskId, kind screenshot/download, handle and relative
name; download requires selector. Optional fullPage, requestId and policyOverrideId
follow discovery. It writes only to the authorized local handle, refusing path
traversal, symlinked destinations and existing files. Results contain local
artifactId/path/handle/name/result and publication not_requested. Publication and
private-content review remain separate from capture. Rules cover supported
routes, not unmanaged CDP or semantic website restrictions.

browser_close defaults to scope task. Explicit scope browser requires actor and
reason and refuses app-borrowed browsers or any peer task. Its supported managed
close reports fresh OS absence of the original process; full child-process residue
requires independent census. Refused or uncertain close never authorizes replay.

These contracts preserve the original app session, durable handoff and Native
viewer. Physical same-process relocation remains a provider gap tracked by
Remote View #578; metadata rebind is not a physical move. Keep the original browser
rather than substituting another profile or reopening it to simulate relocation.


## App-directed browser placement and handoff

An app can pass `hostBinding` to `browser_open` while retaining Agent Browser's
normal task and profile controls. Configure `AGENT_BROWSER_HOSTS_FILE` on both
its MCP transport and runtime host. It names a versioned JSON registry:

```json
{"version":1,"hosts":{"my-app":{"origin":"https://app.example.test","providerApplication":"my-app"}}}
```

The configured `AGENT_BROWSER_REMOTE_VIEW_APPLICATION` must match that host's
provider application. This selects the existing Remote View resource context;
it does not grant access to another application's assignments.

A configured hosted runtime leaves spare-desktop growth and retirement to the
app. Automatic pool maintenance also stays disabled while durable host bindings
remain, including after configuration is removed. Explicit browser tasks retain
their ordinary scoped close behavior.

```json
{"version":1,"hostId":"my-app","participantId":"worker-1","sessionId":"session-1","placement":{"mode":"required","desktop":{"desktopId":"<provider-desktop-id>","generation":1}}}
```

A required desktop must be currently observed in the configured provider pool.
Preferred placement uses `mode: "preferred"` with `desktop` and an ordered
`alternatives` array, and never falls back outside that list. A retained browser
on another desktop reports a conflict without moving or replacing it.

Hosted `browser_handoff` returns the configured app origin's opaque
`/agent-browser/handoff/<id>` URL without requiring a standalone
`AGENT_BROWSER_PUBLIC_ORIGIN`. The app must implement the resolver: validate
its exact participant, saved session, task and current native desktop binding,
then mount the existing authenticated Native viewer. Never substitute the
participant's latest session or use an acquire/launch operation while resolving.
The URL alone does not prove that an app resolver is installed or viewer-ready.
Standalone tasks keep their existing durable handoff behavior.

Use `agent-browser --json mcp host-task <task-id>` for a compact metadata-only
snapshot and `agent-browser --json mcp watch-host-task <task-id>` for an initial
snapshot followed by changed NDJSON events. The dedicated watcher checks only
SQLite/WAL metadata every 250 ms while unchanged, suppresses unrelated commits,
and never launches, focuses or reconciles browsers. Each connection has its own
`watchId` and monotonic sequence; reconnect starts with a full snapshot, not a
replay cursor. Terminate the watcher process for immediate disconnect; a broken
output pipe otherwise exits on the next emitted event. Recorded browser state,
viewer delivery, controller state and account authentication are separate;
metadata-only reads leave unobserved readiness explicitly unverified.


### Attach and explicitly share an app browser

`browser_open` can borrow a currently running app browser instead of launching.
Supply `profile` (the existing profile name), `profileMode: "existing"`, the normal
attribution/task key and configured `hostBinding`. Omit `url`; attachment never
navigates, opens an initial tab, duplicates a profile process or resets work.
Add this `attachment` object:

```json
{
  "version": 1,
  "process": {
    "pid": 1234,
    "startToken": "<current-kernel-process-start-token>",
    "executablePath": "/opt/chromium/chrome",
    "browserFamily": "chromium"
  },
  "profilePath": "/absolute/canonical/app-profile",
  "cdpEndpoint": "ws://127.0.0.1:9222/devtools/browser/<browser-id>",
  "targetId": "<existing-page-target>",
  "sharedWith": []
}
```

The supported local adapter verifies the current process/start/executable,
canonical profile directory, CDP browser PID, existing page and current Native
assignment/window PID before publishing a task. Unsupported platforms or missing
CDP return a concrete capability error without launching. Use the app's native
browser tools when attachment is unavailable. A profile already on another
desktop stays there; supported alternatives are retaining it, selecting another
profile, or an explicit relocation operation when that capability is available.

The original app owns lifecycle. Closing/detaching an attached task preserves
its borrowed initial page and browser process; task-created tabs retain scoped
cleanup. Direct close of a borrowed page is refused. A missing borrowed browser
is reported rather than automatically reopened. The owner may explicitly set
`sharedWith` to exact `{hostId, participantId, sessionId}` recipients by replaying
its original attachment task. Each recipient attaches explicitly with its own
task key and app binding; it cannot change the owner's sharing list. Sharing does
not transfer termination or relocation authority. Metadata reports
`custody: "app_borrowed"`; capability presence is not readiness or account proof.


### Human takeover and return

Viewing alone does not pause automation. Use `browser_control` with `taskId` and
`operation: "status"` (or `view`) to read the current browser-scoped epoch.
Explicit `takeover` requires `expectedEpoch`, an attributable `actor` and a
concrete `reason`. It blocks new mutations across supported MCP, CLI and Service
routes; optional `pauseReads: true` also pauses page observation/capture. Status
and return remain available. Control persists across disconnection and restart.

An eligible human-held, flight-clear `return` observes the exact retained target while ordinary automation stays paused, then commits agent ownership once. A failed pre-commit observation leaves human ownership and the original epoch intact. Inspect status and use a fresh explicit return intent; never replay an uncertain request. Legacy journals, unresolved effects and existing awaiting-observation states keep their explicit reconciliation path.

`return` and deliberate `override` use the current epoch and attribution, then
freshly observe the same retained page before automation resumes. No automatic
return, browser replacement or website-effect replay occurs. Pending dispatched
work retains its observed or uncertain outcome; explicit `reconcile` addresses a
crashed request without repeating it. Override uses existing trusted operator
admission; attribution strings grant no authority. Unmanaged OS/CDP controllers
must cooperate with the current state. See the [control contract](https://github.com/CochranResearchGroup/agent-browser/blob/main/docs/dev/hosted-browser-control.md).

```sh
agent-browser --json mcp host-control TASK status
agent-browser --json mcp host-control TASK takeover 0 operator 'Assist with this task'
agent-browser --json mcp host-control TASK return 1 operator 'Continue after assistance'
```


## Implementation reference

The reference below documents existing integration details. Treat a detail that
conflicts with the governing workflow as an implementation gap to resolve,
rather than a new product requirement.

This guide shows agents and operators how to open a browser through RDP or
Guacamole and preserve one durable link across route changes. The operator
opens an authenticated `/remote-view/<handoff-id>` URL. Provider URLs remain
diagnostic evidence and must not become handoff links.

Authenticated ready handoff resolution also records operator-journey acceptance for the already-selected dashboard generation after validating its live runtime manifest and current owner, route, display, target and provider evidence. This does not select a staged candidate or change fallback and rollback custody. Stale dashboard generations cannot refresh acceptance. An ordinary dashboard without an explicit deployment-generation setting identifies itself by matching its own executable-bound runtime manifest to the selected backend; it cannot borrow a newer backend identity.

Guacamole viewer failures and unusable durable handoff links are appended to
the privacy-bounded Service failure journal. Records contain route and display
correlation identifiers plus a hash of the handoff identifier. They never
contain the operator URL, provider URL, credentials, page content, or request
headers. Reopening the same durable handoff remains the correct reconnect
operation and does not create a replacement handoff solely for diagnostics.

A retained view request is replayed with its original key after an interrupted
reply. When the provider proves that grant terminal, the client records that
outcome and renews the view once under the same durable handoff. Ambiguous
responses preserve the pending request and do not select a replacement key.
For an expired published grant, the session manager validates the retained
issuance against the current assignment and renews once under the same handoff.
A completed issuance whose reply was not published is read from its original
durable mutation record. Its validated expiry permits one renewal after a
desktop-generation change without rewriting that prior intent. Pending,
unexpired, malformed or differently bound records still fail closed. Prior
issuance history remains intact; dashboard presentation reads do not issue grants.
Grant issuance alone does not establish operator-visible readiness.

Use `agent-browser remote-view resolve <handoff-id>` to check an existing handoff
without opening another browser or replacing its URL. It refuses closed sessions.
A converging response is pending readiness; attach only after status is opened
and operatorVisible.state is ready. The session manager may renew an expired
grant while retaining the handoff identity.

A valid retained operator handoff keeps its exact logical session and tab
through browser idle closure and client reconnect. It does not disable the
browser's five-minute idle reaper. After service restart, the reaper loads
retained ownership without waiting for a client request. When every peer is idle and no active operation
holds custody, the process closes once; reconnect through the same handoff
recovers the retained identities after positive process and profile absence. A reused PID is allowed only when current process identity proves it unrelated and a fresh census proves the retained profile absent. Unknown identity or profile occupancy blocks recovery; unrelated processes are preserved.
Explicitly closing the tab or session ends that logical target. A handoff grants
no additional access. Requester-selected retention and browser TTL extensions
remain a separate delivery gate.


> **Important:** Share only `handoffUrl` from a successful remote-view open.
> Never share or bookmark `providerExternalUrl`, a raw Guacamole URL, or a URL
> under `routeBinding`.

The selected route must provide `publicOperatorUrl` for the authenticated
dashboard origin. If it is absent, the open has no durable handoff URL. Agent
Browser does not rewrite a provider or Guacamole origin into the dashboard-only
`/remote-view/<handoff-id>` route.

## Before you begin

When a selected tab is temporarily absent from a dashboard inventory refresh,
the dashboard preserves that tab's identity and waits for it to reappear before
enabling its view or controls. It does not rewrite the selection to another tab
based only on an incomplete inventory.

When opening through `requestServiceRemoteViewOpen()`, pass the access plan's
`browserId` and `sessionName` at the top level. The helper preserves daemon
routing alongside matching handoff metadata. Nested action parameters alone
do not select the daemon session.
Reopening the durable URL preserves the original tab's client access record.
`profile_child_access_record_missing` means a handle operation stopped at child
admission before browser effects. Inspect the Service trace; a returned handle
does not authorize reconstruction of a missing grant.

On Linux, staged workstation migration can discard a process identity from a validated prior boot only when its browser row is missing and no browser projection or runtime-owner reference remains. A reused numeric PID is never signalled. Current-boot mismatches and uncertain boot evidence retain the existing migration checks.

Workstation upgrades bind the packaged Guacamole defaults extension hash to the web container configuration. Changed extension code therefore schedules recreation of that container during Compose reconciliation. This content change leaves the PostgreSQL and guacd service configurations unchanged; verify the served extension after applying an upgrade.

The packaged Guacamole extension preserves text-input preferences but removes
both declarative and controller-startup text-field focus in embedded viewers.
Focus the remote text field
explicitly before typing. This avoids blocked cross-origin autofocus and
keeps dashboard keyboard navigation separate from remote input. Standalone
Guacamole retains its normal autofocus behavior.

You need a configured runtime profile and a ready RDP route. Check the intended
subject without changing it:

```bash
agent-browser doctor remote-view \
  --session <daemon-session> \
  --runtime-profile <profile-id> \
  --json
```

Require `requestedScope.status` and `remoteControl.status` to be `ready`.
Review `globalAdvisories`, but do not let unrelated stale sessions replace the
requested-subject result.

## Handle a checked-out route pool

Route occupancy describes operator presentation, not browser acquisition. If
the requested work does not need a visible desktop, follow the service access
plan and do not reserve or disturb a Guacamole route. A checked-out route pool
does not by itself prove that a managed profile, retained browser, or new
service-owned tab is unavailable.

When presentation is required, use
`service_remote_view_route_preflight` or a scoped remote-view doctor result.
Reuse the requested browser's existing route when possible. If every route is
non-parkable because an active controller is protected, wait and report
`route_pool_exhausted` as a presentation blocker. Request
`service_remote_view_route_switch` only for an explicit presentation
reassignment. Agent Browser decides whether another route can be parked while
preserving its browser process and profile.

Do not close another browser, release another viewer, take over a controller,
or run runtime cleanup to free a route. Add route capacity only after measured
demand shows that the configured pool cannot serve the required number of
simultaneous non-preemptible operator desktops.

For a managed Guacamole route with `providerMode="simultaneous_view"`, the
dashboard backend owns the primary connection for the exact browser, process,
owner generation and display binding. Every viewer uses a restricted sharing
key from that primary's exact tunnel UUID. Closing or reopening a viewer does
not transfer primary ownership. Keys remain transient and must never be saved
or sent as operator handoffs; use the same durable remote-view URL.
During same-handoff revalidation, an existing primary can remain connected only
when the active acquisition proves its previous ready route and exact browser,
owner, process and display binding. A pending route cannot start a new primary.
Provider inventory refresh preserves a current acquisition reservation and its
pending state; provider availability alone does not make it ready.
The same browser keeps its existing capacity slot through revalidation, including
its scene generation and recovery lease. Missing capacity is not created.
A primary guard failure retains a specific safe code: state or authority read
timeout/unavailability is distinct from owner or binding change. A lock timeout
pauses provider writes while the guard tries fresh ownership proof at most three
times, separated by 100 ms. No successful proof is cached. Changed ownership or
other read failures end the primary immediately; exhausted contention ends it
with the original typed cause. Explicit Retry remains available after repair.

A rejected key is discarded and reported through the existing bounded recovery
flow. Automatic recovery may request a fresh key from the same healthy primary;
it cannot restart a failed backend owner or elect a viewer as primary.
The explicit **Retry connection** action can replace a terminated backend primary
once after fresh verification of the same browser, owner, process and display.
It names the exact terminal occurrence; duplicate retries share a starting or
live connection, and an old retry cannot restart a later failed attempt.
Changed or unproven ownership is refused. Retry requests a fresh restricted key
while preserving the browser and durable URL. Binding invalidation closes the
owned tunnel.
The backend records primary termination in the private failure journal with its
typed cause, elapsed lifetime and route/session/display references, even when
no viewer remains to report the failure. Failed primary requests return an
`occurrenceId` for their authenticated journal record and, when known, a
`terminalOccurrenceId` referencing the owner event. They retain `retrySafe=false`.
Backend startup requires the installed provider's trusted header principal and
literal loopback Guacamole origin. Dashboard ingress allows up to 21 seconds
for the bounded primary-start response. An uncertain startup outcome requires
reconciliation before another attempt. Connection readiness does not establish
visible pixels or successful input; those require separate outcome evidence.

Observer-lease acknowledgement preserves the current embedded desktop frame,
including a frame that is still connecting. Use **Reload view** under Advanced
connection controls for an explicit reload.

## Open the browser and copy the durable link

Follow these steps to create one operator-visible browser handoff:

1. Open the route-bound browser:

   ```bash
   agent-browser --json remote-view open https://example.com/secure \
     --service-name codex --agent-name Codex --task-name "Review secure page" --origin-kind agent \
     --runtime-profile operator-review \
     --browser-build stealthcdp_chromium \
     --view-stream-provider rdp_gateway
   ```

2. Require `operatorVisible.state` to equal `ready`. A URL without this proof
   does not prove that the requested browser and tab are visible.

3. Copy `handoffUrl`. Its path is `/remote-view/<handoff-id>`.

4. Give that URL to the operator. The operator signs in to the dashboard when
   prompted and then continues through the same URL.

5. Save the same URL for reconnection. Do not save the current provider route.

## Request a handoff from software

Use `requestServiceRemoteViewHandoff()` when a software client needs a link for
a person. This helper excludes provider connection URLs from its result:

```js
import { requestServiceRemoteViewHandoff } from "@agent-browser/client/service-request";

const handoff = await requestServiceRemoteViewHandoff({
  baseUrl: "http://127.0.0.1:4849",
  serviceName: "OperatorReview",
  agentName: "codex",
  taskName: "review-secure-page",
  runtimeProfile: "operator-review",
  browserBuild: "stealthcdp_chromium",
  viewStreamProvider: "rdp_gateway",
  url: "https://example.com/secure",
});

console.log(handoff.handoffUrl);
// => https://dashboard.example/remote-view/<handoff-id>
```

The lower-level `requestServiceRemoteViewOpen()` helper also requires a durable
handoff URL for real opens. Do not set `allowRawProviderUrl: true` outside an
explicit infrastructure diagnostic.

For software automation, read the valid `serviceTabHandle` directly from the
successful open response with `getServiceTabHandle(response)`. It is returned
at the top level and under `tab.serviceTabHandle`; no additional `tab_new` is
needed. Generic `tab_new` rejects route and display selectors before creating a
job. Route-bound callers must use authenticated `remote_view_open`. Derived
display-allocation identity follows the stable route identity, not an X11
display number that may later be reused by another route.

A retained-browser identity rejection such as
`runtime_handoff_orphan_browser_hint_mismatch` is a failed resolution, not a
successful retryable convergence response. Inspect the profile recovery plan
before retrying; do not change the handoff's browser identity or automatically
reopen a replacement. This rejection reports no effect and does not establish
that the browser is permanently lost. Transient adoption and incomplete
presentation receipts retain their separate convergence behavior.

## Resume software automation from a handoff

Resolve the stored handoff ID first. Then derive the exact retained route and
caller attribution from that response instead of reconstructing them from
processes or provider URLs:

```js
import {
  classifyServiceControlPlaneAuthority,
  deriveServiceRemoteViewHandoffResumeIntent,
  getServiceTabDiagnostics,
} from "@agent-browser/client/service-request";

const intent = deriveServiceRemoteViewHandoffResumeIntent(resolveResponse);
const diagnostics = await getServiceTabDiagnostics({
  baseUrl: "http://127.0.0.1:4849",
  serviceTabHandle: intent.serviceTabHandle,
});
const authority = classifyServiceControlPlaneAuthority(diagnostics);
```

An `observation_only` result permits bounded reads such as diagnostics, probes,
and evaluate calls. Navigation and input require `effect_capable`. An
`unavailable` result means the handoff did not yield a current usable handle.
The derived intent excludes raw provider URLs and local profile paths.

## Reconnect without opening another browser

Open the same `handoffUrl` again. The authenticated dashboard resolves the
handoff ID, requests adoption of the exact retained browser if its original
daemon is gone, and reacquires compatible route, display, and viewer state. If
the recorded CDP target ID expired, it may bind the current tab whose URL still
matches the recorded intent. Normal resolution does not navigate, open a
replacement target, relaunch the browser, change providers, or redirect to a
raw provider URL.

Recovery retains the known route and display when current-boot browser ownership
matches, even if presentation records are pending or orphaned. Physical display
ownership and visibility are verified before the view becomes ready.

The dashboard waits for a ready presentation receipt whose generation,
dashboard deployment, logical browser, daemon owner generation, process
identity, target, and requested provider match the current resolution. A
missing or stale receipt returns a retryable `converging` state, and the
dashboard retries on the same durable URL. A missing retained target fails
closed unless the exact retained browser has a current tab that still matches
the recorded URL intent.

When the dashboard is opened through a non-local origin, CDP screen sockets
use the authenticated same-origin <code>/api/stream/&lt;port&gt;</code> WebSocket
proxy. The external browser is never told to connect to its own loopback
interface. Durable resolution reserves up to 30 seconds for serialized Service
State contention within the existing 90-second job budget.

The durable handoff sidecar preserves the highest recorded presentation
generation when an older service writer saves stale state. Concurrent runtime
updates therefore cannot erase newer ready presentation evidence.

Dashboard login creates a secure cookie for thirty days and renews it on each
authenticated dashboard load. Later durable handoff links opened with the same
public dashboard hostname and browser profile reuse that login. Another
hostname or browser profile has a separate cookie.

Do not run another `remote-view open` only because:

- the Guacamole connection ID changed;
- the route moved to another display;
- the viewer lease expired;
- the dashboard asked you to sign in again; or
- a single-viewer route was taken over by another client.

For a single-viewer disconnect, use **Take control** from the durable handoff
surface. If the tab was deliberately closed, the handoff remains closed until
the operator selects **Reopen tab**. That explicit action is the separate path
that may open and navigate a replacement target.

Dashboard reconnect selects the browser's service-owned RDP stream for viewer
lease authority, even when a CDP stream is currently selected for presentation.
Synthetic daemon stream identifiers are never sent as remote-view route IDs.
Remote-view recovery requests receive a bounded extended proxy budget, and a
typed backend failure code is shown when recovery is rejected.

The workspace viewport keeps browser lifecycle separate from presentation
readiness. A healthy retained browser remains in Active while its view
reconnects. The compact **View** menu uses semantic Desktop, Live page, and
Snapshot names and removes duplicate provider choices. It preserves a usable
operator selection; otherwise it selects a ready source and performs one safe
route or observer reconnect attempt for the current binding. If recovery does
not complete, use the single **Retry connection** action. **Take control** is
always explicit. Reload, route reattach, viewer reconnect or release, and
Guacamole input settings are grouped under **Advanced connection controls**.
Automatic recovery never launches another browser, mutates its profile, takes
control, or releases a viewer.
Route reattach requires configured presentation capacity and reserves the
exact browser, route, and display slot at recovery priority before route
mutation. It rejects active human control, focuses and maximizes the exact
retained browser, and independently re-observes process-bound X11 state before
checkout can report `attached_ready`. Missing process, display, active or
topmost, visible-workspace, geometry, or occlusion evidence returns a typed
operator-presentation blocker without launching a replacement. Route switch
retains its existing recovery reservation contract. Both operations return
matching `recoveryAdmission` and `recoveryRelease` receipts for granted
capacity and leave the retained browser attached.
Route switch applies that reservation as an atomic migration: the source
browser remains retained during admission, an occupied destination stays bound
until parking, and checkout transfers the leased slot before final release.

When the dashboard itself is hosted, a loopback Guacamole iframe is made
browser-reachable by rebasing only its recognized <code>/guacamole/</code> path
onto the configured public origin. The dashboard never embeds its own bare root
as a fallback and never publishes that internal iframe URL as the operator
handoff.

Dashboard users and Guacamole provider users are intentionally distinct. The
forward-auth response retains the authenticated dashboard actor in
<code>X-Agent-Browser-User</code>, while requests under
<code>/guacamole/</code> receive the stable route-authorized principal from
<code>AGENT_BROWSER_GUACAMOLE_HEADER_USER</code> as
<code>Remote-User</code>. Development publication derives that value from the
same operator identity used to provision Guacamole route grants. A healthy
connection row can otherwise appear as “does not exist” when the dashboard
username has no provider permissions.

Remote-headed launches suppress Chrome's crash-restore bubble so an unclean Profile exit cannot cover the control surface; this does not rewrite Profile exit state or restore old tabs.

In embedded Guacamole text-input mode, clicking the remote display directs subsequent keyboard input into the browser. Opening the view leaves dashboard focus unchanged; synthetic mouse events cannot claim keyboard focus.

Development provider readiness verifies that Guacamole serves the exact staged extension source. A stale loaded extension requires provider reconciliation even when containers are healthy.

## Validate from two external clients

Plan 0158 uses the manually dispatched **Plan 0158 External Vantage** GitHub
Actions workflow for off-host evidence. Configure its protected
<code>p158-external-vantage</code> environment with the durable handoff,
dashboard username and password, expected retained identity JSON, a prepared
synthetic pixel-marker screenshot region, and a synthetic-only visual capture
attestation as secrets. The attestation binds a reviewed redaction receipt and
proves forbidden private fields were excluded before capture. The expected
pixel hash binds the exact crop of externally rendered remote pixels. Marker
coordinates with <code>coordinateSpace: remote-view-iframe</code> use iframe CSS

## Troubleshoot an RDP handoff

Use the returned state to choose the next action:

- Missing `handoffUrl`: treat the open as failed, even if a provider URL is
  present.
- `operatorVisible.state=wrong_tab`: inspect the selected target and URL. Do
  not hand off a different visible tab.
- `operatorVisible.state=guacamole_route_unavailable`: repair or reacquire the
  route before sharing a link.
- Dashboard login prompt: authenticate, then reopen the same handoff URL.
- Provider route changed: reopen the same handoff URL and let the resolver
  reacquire it.
- Explicitly closed tab: require the operator to select **Reopen tab**.
- Repeated viewer disconnect: inspect viewer ownership and use **Take over**;
  do not launch a duplicate profile lane.

Run the scoped doctor again when the handoff remains unavailable:

```bash
agent-browser doctor remote-view \
  --session <daemon-session> \
  --runtime-profile <profile-id> \
  --route-id <route-id> \
  --json
```

## Distinguish the three handoff types

Remote-view, executable, and profile-seeding handoffs solve different problems:

- A remote-view handoff gives a person an authenticated browser-view URL.
- The two-phase `agent-browser handoff` prepare, resume, rollback, and finalize
  commands transfer a live browser between daemon executable generations.
- A profile-seeding handoff guides a person through manual authentication and
  later freshness verification.

Do not substitute one handoff type for another.

effects and readback use that scope. A changed kernel start proves the original
ended without attaching or closing its replacement. Live-target readback queries
only the verified original browser and frozen target. New automatic groups with
missing legacy evidence defer before any new claim, native preparation or attempt.
Existing unresolved operations retain original readback obligations; a scoped
runtime request without identity returns `browser_session_idle_original_identity_missing`
and cannot adopt the current PID. Native workflow and installed qualification
remain pending.

`AGENT_BROWSER_DURABLE_HANDOFF_TTL_MS` selects durable link retention (0 means
no time expiry); `AGENT_BROWSER_DISPOSABLE_HANDOFF_TTL_MS` selects disposable
link retention (0 means no time expiry). Both link defaults are 0.
`AGENT_BROWSER_DISPOSABLE_INACTIVITY_MS` selects a positive disposable
inactivity lifetime, defaulting to 86400000 ms. Existing persisted finite policy
values remain configured until explicitly changed; set the matching link setting
to 0 to make newly issued links perpetual.
Policy changes apply to newly issued links. Existing finite links keep their
expiry, including already-expired links. Legacy links with no creation marker
receive creation metadata once without adding or changing their expiry. Extending an unlimited
link preserves its unlimited lifetime. Explicitly closed tasks remain closed.


Explicit native Remote View build selections are retained per runtime profile.
Later launches and retained-browser recovery restore that profile's executable,
even after another client selects a different build or the shared owner restarts.
An incompatible executable already using the profile remains a build conflict.
Legacy records acquire their choice on the next explicit build request; the
upgrade does not guess a missing historical choice from profile contents.

Retained browser recovery reconciles an unobserved launch claim after proving the exact profile has no live process. The original claim remains in history. Provider environment checks run before process admission, so unavailable desktops do not create new launch claims.

## Sharing a profile between tasks

Use one named session and tab per task. When tasks deliberately need the same login and stored browser data, select the same durable profile so they reuse one browser. Give each task its own session name; address commands through that session rather than a global active tab.

Tab-targeted automation can run without either tab being physically visible. Serialize foreground desktop clicks, keyboard input and human control. Separate tabs share cookies, login/logout state and persistent site storage: coordinate account switches, logout and conflicting application changes. Choose separate profiles when independent state is required.

Close only the task's session. Closing one session must preserve its peers; the final session releases the browser. Do not delete the shared profile to clean up a task. If a site requires foreground execution, serialize that part of the workflow.


## Inspect and retain a profile

The tab Properties dialog shows authoritative profile retention as **Throwaway** or **Durable**, and displays a recorded tab creation time even when original attribution is missing. Historical attribution that was never recorded remains unrecorded. Edit **Profile name** and choose **Save name** to change its display label, or choose **Make durable** to retain a throwaway profile across tasks. Both operations preserve the profile ID, browser data directory and open tabs. Promotion removes eligibility for disposable-profile cleanup; normal tab and browser idle policies still apply. If a save cannot be confirmed, refresh the inventory before retrying.


## When the embedded desktop cannot open

The selected desktop error distinguishes handoff preparation from a prepared link whose Native page did not load. An unreadable embedded page offers a Remote View access check without claiming that login expired. Open Remote View reuses the opaque handoff. Refresh browsers reads inventory; Retry explicitly prepares the selected task again. Neither failure starts automatic repair or focus replay.

### MCP handoff service origin

Configure `AGENT_BROWSER_PUBLIC_ORIGIN` with Agent Browser's authenticated HTTPS
origin in its process environment or standard `~/.agent-browser/.env` file
(`AGENT_BROWSER_ENV_FILE` selects another file). Explicit process values take
precedence. Reconnect existing MCP clients after changing startup configuration.
This origin serves opaque `/remote-view/` links; the separate
`AGENT_BROWSER_REMOTE_VIEW_PUBLIC_ORIGIN` locates the native viewer. Origins
retain HTTPS validation; callers do not construct provider URLs.

### Convert an existing task

The browser mode menu offers **Relaunch with CDP** and **Relaunch without CDP** for managed tasks. A successful explicit replacement preserves the logical task, durable profile and original handoff; it changes the physical browser process. Review the affected tasks before selecting relaunch. Unsaved page state and downloads may be lost; unknown URLs and uncertain website submissions are never replayed.

MCP uses `browser_command` with `taskId`, action `mode_convert`, and params containing `operationId`, `mode` (`cdp` or `cdp_free`) and `choice`. Start with `prepare`, then select an offered action. CLI accepts `agent-browser --json mcp mode-convert '{"taskId":"TASK","operationId":"mode-one","mode":"cdp_free","choice":"prepare"}'`. HTTP uses `POST /api/command` with action `browser_session_mode_convert`, the exact `sessionId` and owner `sessionName`, and the same operation fields.

Keep the operation ID after an uncertain reply and select `reconcile`; do not issue another close/open sequence. Close prompts offer focus, graceful retry and consequentially confirmed force close. Native screenshots and input remain separate from authentication proof. Bounded launch recovery is source qualified; broader conversion and installed Native qualification remain incomplete. Do not treat source qualification as accepted installed behavior.

Select `pause_and_relaunch` to hold the operation in `paused` before closing
anything. Affected tasks stay fenced against page and Native automation. Later
select `relaunch`, confirming when the returned action requires it, or cancel
the pause. There is no automatic timed restart. Immediate relaunch is separate.
To cancel conversion at a close prompt, the owner sends Escape and rechecks the
exact live original process and Native window before releasing the operation.
A lost input reply or failed readback keeps custody. Inspect the original page
before continuing; input delivery alone does not prove a page or dialog result.

An already published replacement is a completed physical outcome even when the
final operation-journal write was lost. A restore request then seals the original
operation and reports `mode_operation_already_completed`, preserving the current
browser. Start a new explicit conversion to select another configuration.


To find retained work after reload, send `choice: "inspect"` through the same
`mode_convert` or `profile_duplicate` route. Omit `operationId` to list matching
operations, or include it for one retained operation. Mode lookup requires the
exact task; profile-copy lookup binds the source profile and optional exact
task. The read-only `agent-browser.browser-operations.v1` response includes safe
operation IDs, kinds, task/profile/browser bindings and supported actions. It
never closes, launches or copies a browser. Select the original operation before
continuing; multiple matching copies require an explicit selection. A busy
response identifies the active operation instead of admitting a replacement ID.
The rail reads this owner state when reopened, without persisting profile paths
or credentials in client storage. CLI JSON requests use `choice: "inspect"`
with `mcp mode-convert` or `mcp profile-duplicate`; HTTP uses the same existing
owner actions at `POST /api/command`.

Inspection returns at most 256 matching operations after task/browser filtering,
with the exact active operation and pending work first. `historyTruncated`
reports omitted retained history. Supply a known `operationId` for exact older
readback; inspection and selection still have no browser effects.

Native capture returns PNG image content to MCP agents. Its default tile is bounded to one million pixels. Read `region`, `windowBounds` and `partialWindow`; request an explicit region for remaining pixels. A tile is not represented as a full-window screenshot.


### Browser build selection

The rail menu's **Choose browser build** reads available executable versions,
profile-data version and compatibility uncertainty. Build family, version,
profile and CDP mode remain independent. Family and older-version warnings are
advisory; explicit confirmation cannot make a missing or changed executable
usable. Select the actual native executable, rather than a shell launcher.

MCP: discover `browser_build`, then call `browser_command` with action
`browser_build` and `params: {"profileId":"PROFILE","choice":"inspect"}`.
An optional `taskId` binds the profile to that task. CLI:
`agent-browser --json mcp browser-build '{"profileId":"PROFILE","choice":"inspect"}'`.
HTTP uses `POST /api/command`, action `browser_session_build_select` and the
same fields. Discovery returns opaque `selection` fields (`buildId`,
`expectedSha256`); copy those fields into the consequential request. To review
another installed build, include an absolute `executablePath` in inspection.
Inspecting does not close a browser or modify its profile.

For an inactive profile, use `choice: "select_for_next_launch"`, a stable
`operationId`, selected build fields, `mode: "cdp"` or `"cdp_free"`, and
`ownerConfirmed: true`. This atomically records the pin, mode and receipt.
An omitted mode on later `browser_open` inherits that profile's selected mode;
an explicit mode wins. To open exactly that selection, use `choice:
"open_selected"`, the same profile and selection operation ID. MCP also
requires `serviceName`, `agentName` and `taskName`. It opens a stable task at a
blank page. Read active tasks and `currentSelectionOperationId` through
inspection after a lost reply or reload; do not replay a website submission.
A changed pin, executable bytes or profile must be reviewed again. Generic
MCP `browser_open` can bind `buildSelectionOperationId` for the same guard.

For a running original, prepare the existing `mode_convert` operation with
selected build fields and an independent mode. Confirm only after reviewing
affected tasks and migration risk. Recovery retains that operation ID:
`select_build` chooses another reviewed executable without launching it;
`relaunch` launches after proven absence. `restore_previous` selects the
previous executable and mode when available. It does not restore profile
bytes. Unknown process state remains fenced; never run another browser
against the same writable directory.

For duplicate-and-test, prepare `profile_duplicate` with selected build fields
and mode. Source preparation uses its configured build. The destination pin
and mode are published with the independent copy. Failed launch retains that
copy; reconcile, then retry or confirm `finish_without_opening`. After finishing,
select another build for the destination profile and explicitly open that
selection. This reuses the exact published directory without copying again.

Profile readability, copied cookies, credential-store availability and usable
authentication are separate evidence. A newer build may migrate files; an
older or different build may fail to read them or lose login. Prefer an
independent copy for testing. If login is lost, stop account actions and sign
in explicitly in the chosen browser. Never weaken encryption, export keys or
replace credential stores to manufacture portability. Inspect another build,
use a confirmed original, keep the copy without opening, or cancel.
