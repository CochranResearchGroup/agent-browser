## Question, sources and bound

Which existing Auth Receipts and Agent Browser capabilities support an authenticated-task journey, and which integration or qualification gaps remain? This bounded read-only investigation uses owning source, specifications, live tracker bodies and attributable acceptance notes. It stops at a capability/evidence classification and unresolved decision inputs; it does not select product tradeoffs or execute a login.

## Principal finding

Reuse Auth Receipts as the credential/MFA authority and build on the existing Agent Browser workflow adapters. The immediate gap is more precise than installation: the accepted ordinary-client experience must let an enrolled caller ask for a specific service/account login and reach owner review without prearranging a per-site discovery/use rule or knowing internal source/record IDs. Current canonical source does not provide that path. The latest owning issue explicitly identifies it as a product defect, not a desirable enrollment requirement. [Current ordinary-client requirement](https://github.com/CochranResearchGroup/auth-receipts/issues/81), [canonical discovery and request code](https://github.com/CochranResearchGroup/auth-receipts/blob/e000f82563b445062411592947f3607cfe7c9228/src/credential-service.mjs#L683-L745).

## Current source versus intended ordinary experience

At the inspected Auth commit, discovery skips sources unless current policy admits metadata discovery and throws `auth_not_authorized` when none are admitted. `request_credential` requires `sourceId` and `recordId`; no matching policy produces a denied request. This explains why publishing or installing the current interfaces alone cannot deliver the now-clarified ordinary experience. [Exact implementation](https://github.com/CochranResearchGroup/auth-receipts/blob/e000f82563b445062411592947f3607cfe7c9228/src/credential-service.mjs#L683-L745).

The owning issue was updated during this research (October 25, 2026, 20:44 UTC). Its correction requires: service/account intent, bounded resolution, one owner-reviewable request, genuine account selection only when ambiguous, and owner approval before private release. No per-site allowlist, policy-editor step or source/record IDs may be prerequisite merely to ask. Existing deny/revoke, expiry, exact receiving scope, notifications and no-replay remain. The issue records the specification/status correction on a separate uncommitted reconciliation branch; this note does not call the source repaired. [Owning ordinary-client decision and current gap](https://github.com/CochranResearchGroup/auth-receipts/issues/81).

The fresh enrolled-client preflight reported in that issue reached the login form but was held at discovery with no protected read or input. It does not establish a missing credential or failed provider. The product map should treat this as Auth-owned request-admission work, followed by Agent Browser composition and end-to-end qualification, not prescribe an operator-created standing rule as a workaround. [Recorded ordinary-client preflight](https://github.com/CochranResearchGroup/auth-receipts/issues/81).

## Owner boundaries and remaining decision inputs

1. Auth owns discovery/request admission, current policy, private material, receiver authority, MFA and original-attempt reconciliation. Parent Receipts owns channel delivery and attributable returned actions; Agent Browser should not add a parallel authority or direct Slack polling. [Responsibility contract](https://github.com/CochranResearchGroup/auth-receipts/blob/e000f82563b445062411592947f3607cfe7c9228/docs/receipts-interoperation.md).
2. Agent Browser owns task/profile/browser continuity and composition into useful website work. Provider authentication must not substitute for the requested company/site outcome. Existing playbooks and P279 adapters are adoption inputs, not proof that the first accepted workflow is complete. [Canonical playbook](https://github.com/CochranResearchGroup/agent-browser/blob/7ac52c0691ed8f92f075a965174b013e87a7ebdc/packages/client/src/login-playbook.js).
3. Source supports distinct generic/CDP and native receiver paths. Native readiness must cover actual process/window/control epoch/accessibility/visible origin, and observed input dispatch remains weaker than independent account verification. Existing broad provider capture-isolation hardening is explicitly deferred for the owner-controlled evaluation; do not claim it present or silently convert the deferral into a new prerequisite. [Qualification and custody limits](https://github.com/CochranResearchGroup/auth-receipts/blob/e000f82563b445062411592947f3607cfe7c9228/docs/agents/totp-qualification.md), [evaluation boundary](https://github.com/CochranResearchGroup/auth-receipts/blob/e000f82563b445062411592947f3607cfe7c9228/docs/AUTH_HELPER_REPO_SPEC.md).
4. Method coverage remains a specification input. Email/SMS codes, magic links and persistent production passkeys have a new owning program; do not independently rebuild them in Agent Browser or imply all are installed. Its source/installed/provider gates must be read at adoption time because work is actively changing. [Message authentication and persistent passkeys](https://github.com/CochranResearchGroup/auth-receipts/issues/110).
5. The next human decision should select the initial representative account/site outcomes and intervention behavior, then stage admission repair, existing adapter/playbook composition and bounded real acceptance. This research does not choose those outcomes for the operator.
